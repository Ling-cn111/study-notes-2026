# 第三章：分支管理

## 📖 概述
本章目标：**掌握Git分支的完整生命周期**。你将学会：
- 创建/切换/删除分支（`checkout` / `switch` / `branch`）
- 合并分支（`merge`）
- 变基分支（`rebase`）
- 解决合并冲突（团队协作必修课）
- 理解不同分支策略的使用场景

---

## 1. 为什么需要分支？

**一句话作用**：分支让你在**不影响主代码**的前提下，独立开发新功能、修复bug、实验想法。

**生活类比**：
- 主分支 `main` = 餐厅的**正式菜单**（已上架菜品）
- 功能分支 `feature/login` = 后厨的**实验台**（研发新菜，不影响顾客）
- 开发完成 → 测试通过 → 合并回主菜单

**核心优势**：
- 多人并行开发不同功能，互不阻塞
- 实验性代码失败可直接删除分支，不影响主分支
- 生产环境出bug，可快速切到热修复分支

---

## 2. Git分支的本质（极简原理）

**关键认知**：分支就是一个**指向某次提交的指针**（可移动的标签）。

```
提交历史（每个提交有唯一哈希）：
a1b2c3d ← e4f5g6h ← i7j8k9l  (main)
                      ↑
                    HEAD指向main

创建新分支 feature：
a1b2c3d ← e4f5g6h ← i7j8k9l  (main, feature)
                      ↑
                    HEAD仍指向main
```

- `HEAD` = 当前所在分支
- 切换分支 = 移动 `HEAD` 指针
- 新提交 = 在当前分支上新增节点

---

## 3. git branch —— 管理分支

**作用**：列出、创建、删除分支。

**一句话类比**：查看餐厅后厨有几个实验台，或者新建/拆掉一个实验台。

**常用参数**：

| 参数 | 作用 | 典型用法 |
|------|------|----------|
| `git branch` | 列出所有本地分支（当前分支带*号） | `git branch` |
| `git branch <分支名>` | 创建新分支（但不切换） | `git branch feature-login` |
| `git branch -d <分支名>` | 删除已合并的分支 | `git branch -d feature-login` |
| `git branch -D <分支名>` | 强制删除未合并的分支（危险） | `git branch -D experiment` |
| `git branch -m <旧名> <新名>` | 重命名分支 | `git branch -m feature-login feature-auth` |

**实操示例**：
```bash
# 查看当前分支
git branch
# 输出：* main（星号表示当前分支）

# 创建新分支
git branch feature-hello

# 再次查看（看到新分支但星号仍在main）
git branch
# 输出：
#   feature-hello
# * main
```

**常见误区**：
- ❌ `git branch` 只创建不切换，新手容易忘了切分支就提交（还在main上）
- ❌ 删除分支时如果没合并，`-d` 会报错，需要用 `-D`（但确认你真的不要这些改动）

---

## 4. git checkout / git switch —— 切换分支

**作用**：切换到指定分支，将工作区内容更新为该分支的最新提交。

**一句话类比**：从主灶台走到"登录功能"专用灶台，案板上的菜也跟着切换。

**常用参数**：

| 命令 | 作用 | 典型用法 |
|------|------|----------|
| `git checkout <分支名>` | 切换分支（传统方式） | `git checkout feature-hello` |
| `git switch <分支名>` | 切换分支（Git 2.23+ 推荐） | `git switch feature-hello` |
| `git checkout -b <新分支>` | 创建并切换到新分支 | `git checkout -b feature-login` |
| `git switch -c <新分支>` | 创建并切换到新分支（推荐） | `git switch -c feature-login` |

**实操示例**：
```bash
# 创建并切换到 feature-hello 分支
git switch -c feature-hello

# 验证当前分支
git branch
# 输出：
# * feature-hello
#   main

# 在分支上做修改
echo "Hello from feature branch" > hello.txt
git add hello.txt
git commit -m "添加hello.txt"
```

**终端输出**：
```
Switched to a new branch 'feature-hello'
[feature-hello a1b2c3d] 添加hello.txt
 1 file changed, 1 insertion(+)
 create mode 100644 hello.txt
```

**常见误区**：
- ❌ `git checkout` 同时支持切换分支和恢复文件，容易混淆。建议用 `switch` 切换分支，用 `restore` 恢复文件（第四章讲）
- ❌ 切换分支前**务必提交或暂存当前改动**，否则会丢失修改（Git会阻止你，除非用 `-f` 强制）

## 5. git merge —— 合并分支

**作用**：将指定分支的改动合并到当前分支。

**一句话类比**：把实验台（feature分支）上研发成功的新菜，正式加到主菜单（main分支）里。

**常用参数**：

| 参数 | 作用 | 典型用法 |
|------|------|----------|
| `git merge <分支名>` | 合并指定分支到当前分支 | `git merge feature-hello` |
| `git merge --no-ff <分支名>` | 禁用快进合并，保留分支历史 | 团队规范常用 |
| `git merge --abort` | 放弃合并，回到合并前状态 | 解决冲突时放弃 |

### 场景一：无冲突的"快进合并"（Fast-forward）

**条件**：目标分支是当前分支的直接祖先（没有分叉）。

```
合并前：main → a → b
         feature → a → b → c

合并后：main → a → b → c  (直接移动指针)
```

**实操示例**：
```bash
# 切换到 main 分支
git switch main

# 合并 feature-hello（快进合并）
git merge feature-hello
```

**终端输出**：
```
Updating a1b2c3d..e4f5g6h
Fast-forward
 hello.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 hello.txt
```

**解读**：`Fast-forward` 表示没有分叉，Git直接移动 `main` 指针到 `feature-hello` 的最新提交。

### 场景二：有分叉的"三方合并"

**条件**：两个分支在共同祖先之后都有各自的新提交（形成分叉）。

```
合并前：main → a → b → d
              ↗
         feature → c

合并后：main → a → b → d → e(合并提交)
              ↗        ↗
         feature → c  (合并后仍存在)
```

**实操示例**（模拟分叉后合并）：
```bash
# 在 main 上提交一次
echo "Main update" > main.txt
git add main.txt
git commit -m "main上新增文件"

# 切换回 feature 分支并提交一次
git switch feature-hello
echo "Feature update" > feature.txt
git add feature.txt
git commit -m "feature上新增文件"

# 切换回 main 并合并
git switch main
git merge feature-hello
```

**终端输出**（无冲突）：
```
Merge made by the 'ort' strategy.
 feature.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 feature.txt
```

**解读**：Git自动创建了一个**合并提交**（Merge Commit），它有**两个父提交**（来自main和feature）。

## 6. 冲突解决 —— 团队协作的必修课

**什么情况会冲突**？两个分支**修改了同一个文件的同一行**，或一个分支删除文件而另一个分支修改它。

**冲突发生时**：合并过程会暂停，Git提示冲突文件，需要手动解决。

### 实操示例（制造并解决冲突）

```bash
# 1. 在 main 分支修改 README.md（第1行改成 "Main version"）
git switch main
echo "Main version" > README.md
git add README.md
git commit -m "main修改README"

# 2. 在 feature 分支也修改 README.md（第1行改成 "Feature version"）
git switch feature-hello
echo "Feature version" > README.md
git add README.md
git commit -m "feature修改README"

# 3. 在 main 分支合并 feature（会产生冲突）
git switch main
git merge feature-hello
```

**终端输出**：
```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

### 查看冲突文件

```bash
git status
# 输出：
# On branch main
# You have unmerged paths.
#   (fix conflicts and run "git commit")
#   (use "git merge --abort" to abort the merge)
# 
# Unmerged paths:
#   (use "git add <file>..." to mark resolution)
#         both modified:   README.md
```

打开 `README.md`，会看到冲突标记：
```markdown
<<<<<<< HEAD
Main version
=======
Feature version
>>>>>>> feature-hello
```

**冲突标记含义**：
- `<<<<<<< HEAD` 到 `=======` = 当前分支（main）的内容
- `=======` 到 `>>>>>>> feature-hello` = 被合并分支（feature）的内容

### 解决冲突的步骤

1. **手动编辑文件**，保留想要的内容（或合并两者）
2. **删除冲突标记**（`<<<<<<<`、`=======`、`>>>>>>>`）
3. **标记为已解决**：`git add <文件名>`
4. **完成合并**：`git commit`（会自动生成合并提交信息）

**实操示例**：
```bash
# 编辑 README.md，改为你想要的内容，比如：
echo "Main and Feature merged version" > README.md

# 标记为已解决
git add README.md

# 完成合并提交
git commit -m "合并 feature-hello，解决 README 冲突"
```

**终端输出**：
```
[main a1b2c3d] 合并 feature-hello，解决 README 冲突
```

**常见误区**：
- ❌ 解决冲突时只删除冲突标记而不修改内容 → 合并虽然完成但逻辑错误
- ❌ 用 `git merge --abort` 放弃合并后，又忘记重新处理 → 冲突会一直存在
- ❌ 多人同时改同一个文件时频繁冲突 → 需要团队规范（如分工明确、频繁pull）

## 7. git rebase —— 变基（另一种整合方式）

**作用**：将当前分支的提交"嫁接"到目标分支的最新提交之上，得到更线性的历史。

**一句话类比**：你不是直接把实验台搬回主菜单，而是把实验台上新做的菜，**重新做一遍**放到主菜单后面（看起来像在主菜单上直接做的）。

### merge vs rebase 对比（核心差异）

| | **merge（合并）** | **rebase（变基）** |
|--|------------------|-------------------|
| **历史** | 保留分支分叉，有合并提交 | 线性历史，无分叉 |
| **操作** | 创建合并提交 | 重写提交哈希 |
| **安全性** | 安全（不改已有提交） | 有风险（改写了提交历史） |
| **适用场景** | 公共分支（main） | 私有分支（功能开发） |

**rebase 实操示例**：
```bash
# 当前在 feature 分支上
git switch feature-hello

# 将 feature 变基到 main 的最新提交之上
git rebase main
```

**终端输出**（无冲突）：
```
Successfully rebased and updated refs/heads/feature-hello.
```

**原理示意**：
```
rebase 前：main → a → b → c
           feature → a → b → d

rebase 后：main → a → b → c → d' (d'是重放后的新提交)
           feature → a → b → c → d'
```

**如果 rebase 时有冲突**：
1. 解决冲突（同 merge 的冲突解决）
2. `git add <解决后的文件>`
3. `git rebase --continue`（继续）
4. 或 `git rebase --abort`（放弃）

**何时用 rebase**：
- ✅ 本地分支还未推送到远程 → 放心用
- ✅ 想保持干净的线性历史 → 推荐用
- ❌ **绝不在公共分支（如 main）上对他人已推送的提交做 rebase**

**黄金法则**：**不要变基公共分支上的提交**（其他人基于它的提交都会失效）。

## 8. 分支管理策略（实战建议）

### 常见分支模型

**1. GitHub Flow（简单团队）**
```
main ← 始终可部署
  ↑
feature/xxx ← 从main切出，完成后合并回main
```
- 适合：持续交付的小团队
- 规则：所有功能都从 `main` 切分支，合并后立即删除

**2. Git Flow（复杂项目）**
```
master (生产) ← 只接受 release/hotfix
  ↑
develop (开发) ← 日常开发
  ↑
feature/xxx ← 从develop切出
```
- 适合：有固定发布周期的项目
- 更复杂，需要 `develop`、`release`、`hotfix` 等多类分支

### 日常分支操作流程图

```
创建功能分支 → 开发 → 提交 → 推送远程 → 创建PR/MR
                ↓
           review通过
                ↓
   更新main (git pull) → 本地rebase/merge → push
```

## 🧠 本章小结

- `git branch`：查看/创建/删除分支（管理实验台）
- `git switch`：切换分支（移动工作台）
- `git merge`：合并分支（将实验菜加入主菜单）
- `git rebase`：变基分支（重放提交，保持线性历史）
- **冲突解决**：编辑冲突文件 → `git add` → `git commit`
- **黄金法则**：公共分支用 `merge`，私有分支可用 `rebase`
