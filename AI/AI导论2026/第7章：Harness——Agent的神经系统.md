## 第三板块：系统层——AI如何“行动”

## 第7章：Harness——Agent的“神经系统”

### 7.1 从“模型”到“系统”：为什么Harness成为2026年的核心议题

我们先来做一个思想实验。

假设你面前有两个AI系统：
- **系统A**：搭载了GPT-5.6，但它的Harness很简陋——只能做单轮问答，没有工具调用，没有记忆。
- **系统B**：搭载了开源的Qwen-3，但它的Harness极其复杂——能调用数百个API，有完善的记忆系统，能自主规划多步骤任务。

**在绝大多数真实任务中，系统B的表现会碾压系统A。**

这不是假设。2026年，学术界已经通过大量实验验证了一个反直觉的结论：**Harness的设计差异，能让同一个模型在端到端任务上的成功率波动数十个百分点。** 有一篇论文甚至直接取名为《Don‘t Blame the Large Language Model》（别怪大语言模型），尖锐地指出：我们常常责怪模型不够聪明，但真正的问题往往出在“包裹模型的系统”上。

**那么，Harness到底是什么？**

-   **学术定义**（MemoHarness论文）：Harness是“**将基础LLM转化为可执行Agent的外部控制层**”。它规定了上下文如何构建、哪些工具被暴露、推理如何编排、记忆如何保留、输出如何验证。
-   **产业定义**（微软Agent Framework）：Harness是“**将语言模型转化为Agent的脚手架（Scaffolding）**”。模型本身只能生成文本，要让模型调用工具、完成多步骤任务、记住做过什么、持续工作直到任务完成，你需要一个环绕模型的运行时。
-   **最简洁的公式**（DeepSeek）：**Model + Harness = Agent**。

这个公式意味着：在2026年，当你谈论一个“AI Agent”时，你谈论的从来不是那个模型文件本身，而是**“模型 + 包裹它的那套完整运行时系统”**。

### 7.2 Harness的核心组件架构（深度拆解）

一个完整的Harness到底长什么样？我们把它一层层剥开来看。

**1. 模型接入层（Model Adapter Layer）**

这是Harness的“入口”。它负责对接不同的LLM——无论是OpenAI的闭源API、Anthropic的Claude，还是本地部署的Qwen、DeepSeek。

-   **关键设计**：**热插拔（Hot-Swap）**。在生产环境中，你可能需要根据任务类型动态切换模型——写代码用DeepSeek，复杂推理用GPT-5.6，简单任务用轻量级本地模型以节省成本。现代Harness（如OpenClaw、DeepSeek Harness）都通过统一的Adapter模式支持这种“模型路由”，在运行时根据任务特征选择最合适的模型。
-   **进阶能力**：**混合调度**。一个复杂任务的不同子步骤可以交给不同的模型执行，由Harness负责结果汇聚。这被称为“模型路由”（Model Routing），是2026年降低成本、提升效果的核心工程实践。

**2. 工具调用系统（Tool Use System）**

这是Harness的“手和脚”。模型输出的不再是单纯的“文本”，而是结构化的“工具调用指令”。

-   **函数调用（Function Calling）**：这是最基础的形式。模型输出一个JSON，指定要调用的函数名和参数。Harness解析JSON，执行对应的函数（比如“查天气API”），把结果返回给模型。
-   **PTC（程序化工具调用，Programmatic Tool Calling）**：这是2026年更高级的形态。模型不再只输出“调用哪一个工具”，而是直接**生成一段代码（比如Python脚本）来编排多个工具的执行流程**。比如，模型可以写一段代码：“先查数据库A获取用户ID列表，然后对每个ID调用API B获取详情，最后将结果汇总成CSV文件”。这段代码由Harness在沙箱中执行，执行结果再返回给模型。
-   **执行流水线**：一个成熟的工具调用系统，在工具真正被执行之前会经过多层“关卡”：**Hook（钩子，在调用前/后插入自定义逻辑）→ 审批（需要人工确认高风险操作）→ 权限检查（这个Agent有没有权限调用这个API？）→ 沙箱（在隔离环境中执行）→ 超时控制（防止卡死）**。执行完成后还有**结果改写**和**日志记录**。

**3. Agent循环（Agent Loop）**

这是Harness的“心脏”。它是Agent持续运行的引擎。

-   **经典ReAct范式**：**Re**asoning + **Act**ing（推理+行动）。Agent在一个循环中不断进行“思考-行动-观察”：
    1.  **思考**：LLM分析当前状态，决定下一步做什么。
    2.  **行动**：Harness执行LLM指定的工具调用。
    3.  **观察**：Harness将工具执行结果返回给LLM。
    4.  **循环**：LLM根据新的观察结果，再次思考下一步。直到LLM判断“任务已完成”，输出最终答案，循环终止。
-   **Plan-and-Solve策略**：对于更复杂的任务，Agent在第一步就先生成一个完整的**DAG（有向无环图）**——把大任务拆解成多个有序的、有依赖关系的子任务，然后再按图执行。这种方式更“结构化”，适合有明确流程的企业级场景（如“生成一份周报，需要先拉取数据、然后分析趋势、最后排版”）。
-   **循环终止条件**：如何让Agent知道自己“做完了”？这是一个需要精心设计的问题。常见做法包括：模型输出特殊的“完成”标记、达到最大迭代次数、人工介入叫停。

**4. 记忆系统（Memory System）**

大模型有“金鱼脑”——它的上下文窗口是有限的，而且每次对话结束，它就“失忆”了。记忆系统解决这个问题。

-   **短期记忆**：即上下文窗口内的对话历史。Harness负责把本轮对话的所有交互（用户输入、模型思考、工具调用、执行结果）都维持在上下文里，直到窗口溢出。
-   **长期记忆**：当上下文窗口快满时，Harness会自动对旧的对话进行**压缩/摘要**，存到外部存储中（如向量数据库、知识图谱或简单的文件系统）。当用户再次问起相关话题时，Harness通过**检索**把相关的历史摘要召回，重新注入上下文。
-   **OpenClaw的记忆实践**：它的记忆完全依赖工作区（Workspace）文件，通过`MEMORY.md`、每日日志等多层结构实现持久化。Agent在规划任务时，会主动读取这些“记忆文件”作为决策依据——这使得Agent的“记忆”不仅是被动的上下文，而是主动查阅的“个人笔记”。

**5. 沙箱与安全边界（Sandbox & Security）**

Agent如果获得了执行代码或操作文件系统的能力，它就是一个潜在的“危险分子”。沙箱是它的“笼子”。

-   **代码执行沙箱**：Agent生成的任何代码，都在一个隔离的Docker容器或类似E2B的专用执行环境中运行，无法访问宿主机系统。
-   **权限控制（ACL）**：不同的Agent可以被赋予不同的工具权限。一个“只读Agent”只能查询数据，不能修改数据；一个“部署Agent”有更高的权限，但它的所有操作都会被详细审计。
-   **审批流（Human-in-the-loop）**：对于高风险操作（如“删除生产数据库”、“发送邮件给所有用户”），Harness可以设置为“挂起”，等待人工审批通过后才继续执行。

**6. 上下文管理（Context Management）**

长时间运行的Agent会累积海量的对话历史和工具调用日志，上下文窗口很快就会溢出。

-   **策略组合**：现代Harness通常组合使用多种策略——**滑动窗口**（只保留最近的N轮对话）、**关键信息提取**（用模型自动总结“用户意图”和“已完成任务”）、**摘要压缩**（用一个小模型把长的对话历史压缩成几句话）。
-   **OpenClaw的实践**：当上下文接近窗口极限时，Agent会自动触发“总结旧对话”操作，将总结写入`MEMORY.md`，然后清空上下文，继续运行——这是一种“自我管理的记忆”。

**7. 可观测性与追踪（Observability & Tracing）**

Agent的运行是非确定性的，它可能会“胡思乱想”、走弯路，甚至陷入死循环。可观测性是调试和优化Agent的唯一手段。

-   **追踪（Tracing）**：记录Agent的每一步（思考、工具调用、结果），形成完整的运行轨迹图，方便开发者回放和审计。
-   **指标（Metrics）**：统计任务成功率、平均迭代步数、工具调用失败率、Token消耗量。
-   **集成方案**：微软Agent Framework内置了OpenTelemetry遥测；LangSmith、AgentOps等第三方平台提供专门针对Agent工作流的可视化面板。

### 7.3 设计哲学：为什么“一切皆插件”是Agent运行时的终极形态？

早期的Agent框架（如2023年的LangChain）是“大而全”的——它试图把上面所有组件打包成一个“一体化框架”，开发者只能在这个框架的“牢笼”里做有限的定制。

2026年，主流Harness的设计哲学已经彻底转向了**微内核架构（Microkernel Architecture）**。

**核心思想：核心尽可能小，一切功能都是可插拔的插件。**

-   **微内核**（如DeepSeek Harness基于的**Cordis框架**）只做一件事：**管理插件的加载、卸载和依赖关系**。它本身几乎“什么都不干”，不承载任何Agent的具体能力。
-   **插件**：模型接入、工具调用、记忆策略、沙箱策略……所有的核心功能都被拆分成独立的插件模块。

**为什么这种“极致解耦”是2026年的最优解？**

1.  **应对模型快速迭代**：今天是GPT-5.6，明天可能是GPT-6或更强的开源模型。如果一个框架把模型接入“写死”了，每次新模型发布都要等框架升级。而插件化架构下，开发者只需自己写一个新插件，就能让Harness支持任意新模型，热插拔即可。
2.  **应对场景碎片化**：一个企业级RAG Agent和一个游戏NPC Agent，对“记忆”的要求完全不同。前者需要向量数据库，后者只需要简单的角色设定。一体化框架会让前者变得臃肿，而后者又觉得太重。插件化允许开发者“按需装载”，构建最精简的运行时。
3.  **可组合性与故障隔离**：插件之间通过声明依赖来建立协作关系。当一个插件失败或卸载时，依赖它的插件可以收到通知并优雅降级，而不是整个系统崩溃。

**Cordis的“时空可组合性”**：这是实现微内核架构的核心机制。“时间”指插件卸载后，其注册过的服务、事件和副作用能够随之撤销，不会留下“残留状态”污染系统；“空间”指插件可以声明依赖，并在其他组件变化时自动重新建立协作关系。这一套设计已在Koishi聊天机器人框架中运行四年，超过4000个社区插件的生态验证——它不是纸上谈兵。

### 7.4 2026年主流Harness实现对比

2026年，市面上已经有了多条成熟的Harness技术路线：

**路线一：DeepSeek Harness（开源，极致插件化）**

-   **发布时间**：2026年8月13日正式发布v0.1开发者预览版，MIT协议开源。
-   **设计理念**：一切皆插件。基于Cordis微内核框架构建，将模型、工具、技能、会话、沙箱、存储、循环、调度、UI全部拆分为独立的插件模块。
-   **四种预置模式**：标准模式（完整工具组合）、PTC模式（模型生成代码编排工具链）、极简模式（仅Shell和文件编辑）、创造模式（Agent可检查运行时、在内存中调试插件、组合新模式）。
-   **定位**：适合追求极致灵活性、希望深度定制Agent运行时的开发者和研究机构。

**路线二：OpenClaw（开源，操作系统级自动化）**

-   **核心理念**：云端大脑 + 本地肢体。
-   **三层架构**：模型层（Brain，统一LLM接口）→ 智能体层（Planner，任务编排引擎，将指令拆解为DAG）→ 技能层（Claws，5700+个标准化原子操作插件）。
-   **部署架构**：以Gateway（网关）为核心的星型架构。Gateway是唯一对外暴露的控制平面，负责路由、会话管理和安全边界；每个Agent拥有独立的身份、上下文和工具集。
-   **定位**：适合需要操控操作系统、浏览器、文件系统等“本地环境”的自动化场景。

**路线三：微软Agent Framework（闭源，一站式的企业级方案）**

-   **发布时间**：2026年4月达到1.0 GA（正式发布）。
-   **设计理念**：Batteries-included（开箱即用）。提供完整的Agent运行时，包含循环、规划、记忆、上下文管理、审批和OpenTelemetry遥测。
-   **定位**：适合微软生态内的企业用户，追求稳定性和低维护成本。

**路线四：闭源SDK（OpenAI / Anthropic）**

-   OpenAI Agents SDK和Anthropic Claude Agent SDK提供了轻量级的Harness实现——主要包含工具定义、Agent交接、护栏、会话和追踪。
-   **定位**：与自家模型深度绑定，适合快速构建PoC，但“锁定效应”强，难以迁移到其他模型。

**选型建议**：如果你追求极致的灵活性和对未来的适应性，DeepSeek Harness的插件化路线是首选；如果你需要操控Windows/浏览器等操作系统级任务，OpenClaw的生态最成熟；如果你是抱着“开箱即用”心态的企业IT团队，微软Agent Framework最省事。

### 7.5 前沿：Harness本身的进化

Harness并不仅仅是一个“静态的脚手架”。2026年最激动人心的前沿趋势是：**Harness本身也在变聪明**。

**趋势一：Harness自我优化（Harness Learning）**

-   **MemoHarness（2026年7月）**：提出Harness应该从自己的过往执行中“学习经验”。它将Harness分解为六个可编辑的控制面（上下文、工具、生成、编排、记忆、输出），并构建一个**双层经验库**来记录“什么策略有效、什么策略导致了失败”。当一个新任务到来时，Harness会检索过往的成功经验，调整自己的控制策略，而不是每次都“从零开始”试错。
-   **Meta-Harness**：更进一步——把Harness本身的代码也作为“可搜索和优化的对象”。当现有Harness设计无法满足任务需求时，Agent可以自动修改Harness插件的逻辑（比如调整工具调用的超时阈值、改变记忆摘要的频率）。

**趋势二：Harness作为评估基础设施**

-   **ProofAgent Harness（2026年5月）**：将AI Agent的评估从“静态跑分”转变为“可重复、可审计的压力测试”。它通过构造对抗性环境（如故意返回API错误、提供模糊信息），测试Agent的鲁棒性和容错能力——这正是Harness在测试场景中被当作“练兵场”使用的范例。

**趋势三：Harness引导性能优化**

-   **FlashRT（2026年7月）**：一个引导Coding Agent将“参考实现”（reference implementation）优化为“多GPU部署方案”的Harness。它让Agent在被Harness引导的过程中，逐步将简单的Python原型改写成能充分利用NVIDIA B200算力的生产级代码，实现高达70倍的延迟降低——这说明Harness本身已经成为性能工程的载体，而不只是调用工具的壳。

### 本章小结

-   **Harness** 是2026年AI讨论的核心概念。它不是一个“辅助工具”，而是定义Agent能力上限的**决定性因素**。公式 **Model + Harness = Agent** 应作为你的核心认知。
-   Harness的核心组件包括：**模型接入层**、**工具调用系统**（含PTC）、**Agent循环**（ReAct/Plan-and-Solve）、**记忆系统**、**沙箱安全**、**上下文管理**和**可观测性**。
-   2026年的设计哲学已经全面转向**微内核+插件化**（以DeepSeek Harness及其背后的Cordis为典型代表），目标是应对模型能力的快速迭代和应用场景的碎片化。
-   前沿趋势显示，**Harness本身正在进化**——它学会了从经验中优化自己，成为评估基础设施，甚至引导代码性能优化。
