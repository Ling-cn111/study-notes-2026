# **第五章 数据库与后端服务**

数据库是项目的记忆。用户注册了账号、发了帖子、下了订单、上传了文件，这些数据都得存起来。数据库选错了，后期迁移非常痛苦；选对了，开发顺滑、查询高效、维护省心。后端服务则是数据库前面的那层逻辑：处理请求、验证身份、读写数据、返回结果。对新手来说，数据库和后端服务往往是最容易忽略、也最容易踩坑的部分。这一章会把常见数据库类型、BaaS 服务、选择方法讲清楚，帮你建立完整的后端认知。

## **5.1 关系型数据库**

关系型数据库是最传统、最成熟的数据库类型。它用表格存数据，表与表之间通过外键关联，支持 SQL 查询、事务、约束。你可以把它想象成多个 Excel 表格，每个表有固定的列，每行是一条记录，表之间可以互相引用。关系型数据库的核心优势是：数据结构清晰、查询灵活、事务安全、生态成熟。

关系型数据库适合大多数项目。只要你的数据有明确结构，比如用户、订单、文章、评论、商品，关系型数据库都是稳妥选择。它支持复杂的联表查询、聚合统计、事务回滚，能保证数据一致性。银行转账、电商下单、库存扣减，这些场景必须用事务，关系型数据库是首选。

**PostgreSQL** 是当前最推荐的关系型数据库。它功能强大，支持 JSON、数组、全文搜索、地理信息、向量扩展（pgvector）。它开源、稳定、性能好，社区活跃，云托管选择多。Supabase、Railway、Render、AWS RDS、Google Cloud SQL 都支持 PostgreSQL。对新手来说，PostgreSQL 是默认选择，除非你有特殊理由选别的。

**MySQL** 是另一款流行的关系型数据库，历史悠久，教程多，Web 项目常用。WordPress、PHP 生态大量使用 MySQL。它性能好、部署简单、云托管丰富。但功能上比 PostgreSQL 少一些，比如 JSON 支持较弱、向量扩展不如 pgvector 成熟。如果你用 PHP 或传统 Web 项目，MySQL 很合适。

**SQLite** 是轻量级关系型数据库，整个数据库就是一个文件，零配置，无需服务器。它适合本地应用、原型、小工具、移动端。比如你做一个个人记账工具，用 SQLite 就够了。但 SQLite 不适合高并发写入，不适合多用户同时访问，不适合大规模数据。新手做小项目，SQLite 是最快上手的。

关系型数据库的避坑提醒：不要因为“NoSQL 更灵活”就放弃关系型；不要小看事务，涉及钱和库存必须用事务；不要在生产环境用 SQLite 做多用户服务；不要忘记备份，数据库丢失不可逆。

新手建议：不确定就选 PostgreSQL。本地小工具选 SQLite。PHP 老项目或简单网站选 MySQL。云托管优先选 Supabase、Neon、Railway、Render。

## **5.2 非关系型数据库**

非关系型数据库，也叫 NoSQL，不强制表格结构。它有很多类型：文档型、键值型、列族型、图数据库。最常见的是文档型 MongoDB 和键值型 Redis。NoSQL 的优势是灵活、可扩展、适合非结构化数据。但灵活也是双刃剑：没有 schema 约束，容易数据混乱；不支持复杂事务，一致性弱；查询能力有限。

**MongoDB** 是文档型数据库，数据以类似 JSON 的文档存储。你可以把不同结构的记录放在同一个集合里，不需要提前定义表结构。MongoDB 适合快速变化的数据、日志、内容管理、原型。比如你做一个爬虫，抓到的网页结构不固定，MongoDB 很方便。但 MongoDB 不适合强关系数据，比如订单和用户关联，后期查询会很痛苦。新手如果选 MongoDB，要注意：不要因为它“灵活”就乱存数据，仍然要设计结构；不要忽略索引，否则查询很慢；不要用它替代关系型数据库做核心业务。

**Redis** 是内存键值数据库，速度极快，支持字符串、列表、哈希、集合、有序集合、发布订阅、过期时间。Redis 通常用作缓存、会话存储、消息队列、排行榜、限流。比如你把数据库查询结果缓存到 Redis，下次直接读内存，速度快几十倍。Redis 不适合做持久化主数据库，虽然支持持久化，但内存成本高，数据可能丢失。新手建议：小项目可以先不用 Redis，等有性能需求再加。

其他 NoSQL 还有 Cassandra（列族，适合大规模写入）、Neo4j（图数据库，适合社交关系）、Elasticsearch（搜索引擎，适合全文检索）。这些属于特定场景，新手先不用碰。

避坑提醒：不要因为“灵活”无脑选 MongoDB；不要把 Redis 当主数据库；不要忽略数据建模，NoSQL 也需要设计；不要忘记备份和监控。

新手建议：核心数据用 PostgreSQL，缓存用 Redis，日志或灵活结构用 MongoDB。小项目可以先只用 PostgreSQL，它能覆盖大部分需求。

## **5.3 向量数据库**

向量数据库是 AI 应用兴起后变得重要的数据库类型。它存储和检索向量（embedding），用于语义搜索、推荐、RAG（检索增强生成）。传统数据库用精确匹配或关键词搜索，向量数据库用相似度搜索。比如你问“如何学习编程”，向量数据库能找到语义相近的“编程入门方法”“新手学代码”等文档，即使关键词不完全匹配。

向量数据库的常见选择有：**pgvector**、**Chroma**、**Pinecone**、**Weaviate**、**Milvus**、**Qdrant**。pgvector 是 PostgreSQL 的扩展，让你在关系型数据库里直接存向量、做相似度查询。它的优势是简单、统一、不用额外服务，适合小中型 AI 应用。Chroma 是轻量级向量数据库，本地运行，适合学习和原型。Pinecone 是托管向量数据库，省心但收费。Weaviate、Milvus、Qdrant 更专业，适合大规模生产。

新手做 AI 应用，建议先用 pgvector 或 Chroma。pgvector 适合你已经在用 PostgreSQL 的情况，数据统一管理。Chroma 适合快速实验，几行代码就能存和查。等数据量大了、性能要求高了，再考虑专业向量数据库。

避坑提醒：不要一上来就上 Pinecone 或 Milvus，成本和复杂度高；不要忽略嵌入模型的选择，不同模型效果差异大；不要忘记分块策略，文档切分影响检索质量；不要忽略元数据过滤，纯向量搜索有时不够准。

新手建议：AI 知识库先用 pgvector 或 Chroma。数据量小用 Chroma，数据量中等用 pgvector，数据量大再考虑专业向量库。

## **5.4 BaaS（后端即服务）**

BaaS 是 Backend as a Service 的缩写，意思是“后端即服务”。它把数据库、认证、存储、API、实时推送、云函数都打包好，你不需要自己搭后端服务器，直接调 SDK 就能用。对新手和快速原型来说，BaaS 是极大的加速器。

**Supabase** 是目前最推荐的开源 BaaS。它基于 PostgreSQL，提供数据库、认证、存储、实时订阅、边缘函数、自动生成 API。你可以用它的控制台建表，前端直接调 SDK 读写数据。Supabase 的优点是：开源、基于 PostgreSQL、可导出数据、免费层慷慨、文档好、AI 友好。缺点是：复杂业务逻辑仍需自己写函数，国内访问速度可能不稳定。

**Firebase** 是 Google 的 BaaS，提供 Firestore（NoSQL）、认证、存储、托管、云函数、推送。Firebase 生态成熟，移动端支持好，和 Google Cloud 深度集成。缺点是：NoSQL 数据结构限制，复杂查询弱；绑定 Google 生态，迁移困难；国内访问可能受限。

其他 BaaS 还有 AWS Amplify、Appwrite、PocketBase。PocketBase 是开源单文件后端，适合小项目。Appwrite 是开源 Firebase 替代。

BaaS 适合快速原型、小团队、个人项目、不想写后端的人。但 BaaS 不适合复杂业务、高并发、深度定制、数据合规要求高的场景。

避坑提醒：不要把所有逻辑都放在前端，敏感操作要放云函数；不要忽略数据导出，避免锁定；不要忽视免费层限制，流量大了可能收费；不要用 BaaS 做需要复杂事务的核心业务。

新手建议：快速原型选 Supabase。移动端和 Google 生态选 Firebase。小工具选 PocketBase。想开源可控选 Supabase 或 Appwrite。

## **5.5 后端服务与部署平台**

除了数据库和 BaaS，后端服务还包括服务器、容器、Serverless、云存储、认证服务、消息队列等。对新手来说，不需要全部自己搭，很多平台提供托管服务。

**Serverless 函数**：你只写函数，平台负责扩容、运维。适合 API、定时任务、Webhook。常见有 Vercel Functions、Netlify Functions、AWS Lambda、Cloudflare Workers。优点是省心、按量付费；缺点是冷启动、调试难、厂商锁定。

**容器与云服务器**：你打包 Docker 镜像，部署到云服务器或容器平台。适合需要完全控制、复杂依赖、长运行服务。常见有 Docker、Railway、Render、Fly.io、AWS ECS、Google Cloud Run。新手可以用 Railway 或 Render，简单好用。

**云存储**：存图片、视频、文件。常见有 AWS S3、Cloudflare R2、Supabase Storage、Firebase Storage。新手用 Supabase Storage 或 Cloudflare R2，便宜好用。

**认证服务**：处理注册、登录、OAuth、权限。常见有 Supabase Auth、Firebase Auth、Auth0、Clerk、NextAuth。新手用 Supabase Auth 或 Clerk，省很多事。

**消息队列**：处理异步任务、解耦服务。常见有 Redis、RabbitMQ、Kafka。新手小项目先不用，等有异步需求再说。

避坑提醒：不要过早引入复杂后端服务；不要忽略冷启动和延迟；不要忘记环境变量和密钥管理；不要把所有东西绑在一个厂商上。

新手建议：前端部署用 Vercel / Netlify / Cloudflare Pages。后端部署用 Railway / Render / Fly.io。数据库用 Supabase / Neon / Railway。存储用 Supabase Storage / Cloudflare R2。认证用 Supabase Auth / Clerk。先跑通，再优化。

## **5.6 如何根据项目需求选择数据库与后端服务**

选择数据库和后端服务，可以按下面几个问题来决策。

第一，数据结构是否固定？固定选关系型，不固定选文档型，缓存选键值型，AI 检索选向量型。大多数项目核心数据用关系型，辅助用其他。

第二，是否需要事务？涉及钱、库存、订单，必须关系型 + 事务。NoSQL 事务弱，不适合核心业务。

第三，数据量多大？小项目 SQLite 就够，中等 PostgreSQL / MySQL，大规模考虑分库分表或 NoSQL。新手不要提前优化。

第四，并发多高？低并发 SQLite 也行，中等 PostgreSQL / MySQL，高并发加 Redis 缓存，再高考虑分布式。

第五，是否需要 AI 检索？需要就加 pgvector 或 Chroma，不需要就不碰向量数据库。

第六，是否想快速原型？想快用 Supabase / Firebase，不想写后端。想控制用 FastAPI + PostgreSQL。

第七，预算多少？免费优先 Supabase、Neon、Railway、Render、SQLite。付费考虑云厂商托管。

第八，部署在哪里？国内考虑备案、访问速度、云厂商。海外用 Vercel、Supabase、Railway 方便。

第九，团队能力如何？只有你一个人，选托管服务。有后端，可以自建。有运维，可以上容器。

第十，未来要不要迁移？要迁移就选开源、标准 SQL、可导出数据的方案。避免深度绑定。

新手最稳的组合是：PostgreSQL + Supabase（或 Neon）+ Vercel / Railway。前端 Next.js，后端 FastAPI 或 Next.js API Routes，数据库 PostgreSQL，认证 Supabase Auth，存储 Supabase Storage。这套组合覆盖大部分 Web 和 AI 应用，成本低，AI 友好，学习资源多。

## **5.7 本章小结**

数据库是项目的记忆，后端服务是项目的神经。关系型数据库适合大多数项目，PostgreSQL 是默认推荐。NoSQL 适合灵活结构和缓存，Redis 做缓存，MongoDB 做文档。向量数据库用于 AI 检索，新手先用 pgvector 或 Chroma。BaaS 让新手快速拥有后端，Supabase 和 Firebase 是主流。后端服务尽量用托管平台，减少运维负担。

避坑核心：不要过度设计，不要盲目追新，不要忽略备份和安全，不要忘记数据导出。先跑通，再优化。先上线，再完美。
