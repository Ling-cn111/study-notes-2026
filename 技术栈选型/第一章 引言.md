# **第一章 引言**

## **1.1 技术栈到底是什么**

很多人第一次听到“技术栈”这个词，会以为它只是“选一门编程语言”。其实不是。技术栈是一个项目从开发到上线所需要的整套技术组合。它通常包括：编程语言、前端框架、后端框架、数据库、部署平台、第三方服务、开发工具、版本管理、测试方式等等。你写一个网页，前端用什么框架，后端用什么语言，数据存在哪里，最后部署到哪个平台，这些选择加在一起，才叫技术栈。

举个例子。假设你要做一个个人博客。一种常见技术栈是：Next.js + TypeScript + Tailwind CSS + Markdown + Vercel。Next.js 负责页面和路由，TypeScript 提供类型检查，Tailwind 负责样式，Markdown 存文章，Vercel 负责部署。这套组合很轻，新手一两天就能上线。另一种技术栈是：Rust + Actix + PostgreSQL + Docker + Kubernetes + 自建服务器。它当然也能做博客，甚至性能更强、控制力更高，但对新手来说，可能两周还在配环境，博客一篇文章都没写。这就是技术栈选择带来的差别。

所以，技术栈不是越高级越好，也不是越流行越好。它更像出门选交通工具：短途骑车最方便，长途坐高铁最快，搬家得用货车。你非要骑共享单车跨省，不是车不好，而是场景不对。

## **1.2 为什么技术栈选择重要**

技术栈选择之所以重要，是因为它会直接影响你项目的六个方面。

第一，开发速度。选对了技术栈，你可以把精力放在功能上；选错了，大量时间会消耗在环境配置、依赖冲突、版本不兼容上。新手最容易卡住的地方，往往不是写业务逻辑，而是“为什么跑不起来”。

第二，学习成本。新手的时间有限。如果同时学前端框架、后端语言、数据库、容器编排、云服务，很容易崩溃。技术栈选择的一个重要目标，是让你在最小知识范围内先做出一个能跑的东西。

第三，维护成本。项目上线不是终点，而是起点。后面要改 bug、加功能、升级依赖。如果选了一个文档少、社区小、更新频繁破坏兼容的框架，维护会非常痛苦。主流技术栈的好处是：遇到问题，大概率已经有人问过，AI 也更容易给出正确代码。

第四，部署成本。有些技术本地免费，上线就烧钱。比如某些托管数据库、AI API、对象存储、流量费用。新手往往只看开发阶段，忽略上线后的账单。技术栈选择必须把部署成本算进去。

第五，AI 协作效果。Vibe coding 的核心是让 AI 帮你写代码。但 AI 不是万能的。主流语言和框架的语料多，AI 生成的代码更可靠；冷门技术、刚发布的框架、文档稀少的库，AI 很容易编造 API 或写出过时代码。所以，技术栈的“AI 友好度”已经成为一个现实指标。

第六，职业可迁移性。你学的东西是否能在其他项目、其他公司、其他场景继续用。JavaScript、Python、Java、Go 这些主流语言，学了不亏。某些过于小众的技术，可能只在一个项目里有价值。

一句话总结：技术栈选择决定了你是在“做项目”，还是在“跟工具搏斗”。

## **1.3 新手常见误区**

新手在技术选型上踩的坑，其实高度相似。下面这些误区，几乎每个人都会遇到至少三四个。

**盲目追新**。看到某个新框架很火，就立刻想用。结果发现文档不全、教程很少、AI 经常写错、社区没人回答。避坑建议是：新东西可以了解，但主力项目尽量用生态稳定的技术。想尝鲜，可以开一个小 demo，不要拿主项目冒险。

**过度设计**。个人博客上微服务，小工具上 Kubernetes，内部系统上消息队列。这些技术本身没错，但需要配套的运维、监控、团队能力。新手项目最稳的路线是：先单体应用，先一个数据库，先托管部署。等真的有流量、有团队、有痛点，再拆。

**忽略生态**。选了一个很小众的库，遇到问题搜不到答案，AI 也不认识。生态包括：文档、教程、GitHub 活跃度、包下载量、Stack Overflow 问答、招聘需求。选型时不要只看“它看起来优雅”，要看“我卡住时有没有人帮我”。

**忽略部署成本**。本地跑得好好的，上线发现数据库要钱、AI API 要钱、流量要钱、冷启动很慢。避坑建议：项目早期就用免费层或低成本方案，比如 Vercel、Netlify、Supabase、SQLite、Render。先算一笔账，再决定要不要上云数据库、GPU、付费 API。

**AI 生成代码不审查**。这是 vibe coding 新手最容易犯的错。AI 可能生成有安全漏洞的代码，可能把密钥写死，可能引用不存在的包，可能版本不兼容。避坑建议：逐行审查，跑测试，查官方文档，密钥放环境变量，依赖锁版本。

**低估学习曲线**。Rust、Kubernetes、分布式系统、函数式编程，不是一周能掌握的。新手如果一上来就选这些，很容易放弃。避坑建议：先学能出成果的，先做能上线的，再逐步深入。

**什么都想学**。前端、后端、移动、AI、区块链一起学，最后什么都不精。避坑建议：先深后广。用一个完整项目打通一条链路，再扩展。

**只看语言排行榜**。排行榜高不代表适合你。Java 排名高，但你不做企业后端，可能没必要。Python 排名高，但你要做高性能游戏服务器，可能不合适。选型要看场景、团队、生态、部署。

**不做最小验证**。选完技术栈直接开大项目，写到一半发现某关键功能不支持。避坑建议：先做最小原型，只做登录 + 一个核心功能 + 部署。跑通再扩展。

**忽略数据库选择**。关系型数据用 NoSQL，后期查询痛苦；小工具上重型数据库，部署麻烦。避坑建议：不确定就选 PostgreSQL；本地小工具选 SQLite；缓存选 Redis；AI 检索选 pgvector 或 Chroma。

**忽略安全与合规**。用户密码明文存储、密钥提交到 GitHub、爬虫违反规则、没有隐私政策。避坑建议：用成熟框架的认证，环境变量存密钥，最小权限，了解基本法规。

**过早优化**。还没用户就优化性能，还没流量就考虑分布式。避坑建议：先跑通，再优化。性能问题等有数据再说。

**不写文档和测试**。三个月后自己都看不懂，改一个功能崩三个地方。避坑建议：README 写清楚怎么跑，关键逻辑写测试，提交信息写明白。

**锁定厂商**。深度绑定某个平台，想迁移时发现数据拿不出来。避坑建议：核心数据可导出，尽量用开源标准，不要把业务逻辑写在平台专有服务里。

这些误区不需要一次全部避免，但你要知道它们存在。每次选型时，对照一遍，能省很多时间。

## **1.4 本教程如何使用**

这本教程不是让你背下所有技术，而是帮你建立一套选型思路。建议你这样使用：

先读第二章，确定你的产品形态。是 Web、移动、桌面、小程序、API、AI 应用，还是自动化脚本？形态不同，技术栈差别很大。

然后读第三章到第五章，了解主流语言、框架、数据库。不需要全部掌握，只需要知道每个东西大概适合什么场景。

接着看第六章的对比表，快速筛选。再用第七章的决策流程，一步步缩小范围。选完之后，看第八章避坑清单。最后，第九章和第十章讲怎么和 AI 协作，以及一个可以直接复制的提示词模板。

读的时候，建议你准备一个笔记，写下：项目目标、目标用户、核心功能、团队情况、时间预算、预算、部署地区、你的技术偏好。这些信息越清楚，选型越准。如果你用 AI 帮你选，这些信息就是最重要的输入。

另外，不要试图一次读完就做出完美决定。技术栈是动态的。你可以先选一套默认栈，做出最小原型，再根据真实问题调整。新手最怕的不是选错，而是选了半天不动手。

## **1.5 给 vibe coding 入门者的一句话**

AI 能帮你写代码，但不能替你承担选型后果。你选了一个冷门框架，AI 可能也救不了；你选了一个主流技术栈，AI 就能成为很强的助手。所以，vibe coding 的正确姿势是：主流技术栈 + 清晰需求 + 小步验证 + 人工审查。AI 负责加速，你负责决策。

技术栈选择不是一次定终身，而是随着项目阶段不断调整的过程。早期追求快，中期追求稳，后期追求可维护和可扩展。先跑通，再优化；先上线，再完美。记住这句话，你后面会少走很多弯路。
