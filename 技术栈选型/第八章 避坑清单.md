# **第八章 避坑清单**

技术栈选型这件事，做对不容易，但做错很容易。而且很多错误不是能力问题，而是认知盲区。新手踩的坑高度相似，因为大家面对的信息环境差不多：网上教程众说纷纭，技术博主各推各的，AI 回答也不一定靠谱。这一章把最常见的坑逐条列出来，每条给出简短建议。你可以把它当检查表用，每次选型时对照一遍，能省下大量时间和金钱。

## **8.1 过度设计**

这是新手最容易犯、后果最严重的错误。具体表现：个人博客上微服务，小工具上 Kubernetes，内部系统上消息队列，还没用户就考虑分库分表，还没上线就搭 CI/CD 流水线。这些技术本身没问题，但它们需要配套的运维能力、监控体系、团队协作。一个人做项目，上微服务意味着你要维护多个服务、处理服务发现、调试分布式事务，工作量翻十倍，收益却接近零。

避坑建议很简单：先单体，后拆分。先一个数据库，后读写分离。先托管部署，后自建集群。先跑通，后优化。等你真的遇到瓶颈——比如数据库扛不住了、部署太慢了、团队协作混乱了——再引入对应技术。技术是为了解决问题，不是为了证明水平。一个能上线的单体应用，远比一个跑不起来的微服务架构有价值。
>编者补充：项目设计要着重考虑第一性原理和盖尔定律

## **8.2 盲目追新**

每年都有新框架、新语言、新工具出现，而且宣传都很猛。新手容易被“这个比 React 快十倍”“这个将取代 Python”之类的标题吸引，立刻想用到主项目里。结果发现：文档不全、教程很少、AI 经常写错、社区没人回答、依赖不稳定、升级频繁破坏兼容。你花在踩坑上的时间，远超它带来的收益。

避坑建议：新东西可以了解，但主项目用生态稳定的技术。想尝鲜，开一个小 demo，单独玩，不要拿主项目冒险。判断一个技术是否成熟，看几个指标：GitHub 最近提交是否活跃、Issue 回复是否及时、包下载量是否稳定增长、Stack Overflow 是否有足够问答、生产环境案例是否够多。如果这些都不行，再酷也别用。

## **8.3 忽视生态**

生态比语言本身更重要。一个语言再优雅，如果没有成熟的库、没有活跃的社区、没有足够的教程，你遇到问题只能自己啃源码。新手往往只看语言特性，忽略生态大小。比如有人被 Rust 的性能吸引，但做 Web 后端时发现某些库还不成熟，开发效率远不如 Python。

避坑建议：选型时先看生态。有没有成熟的 Web 框架？有没有好用的 ORM？有没有认证、支付、邮件、队列的库？社区活跃吗？文档好吗？招聘多吗？AI 熟悉吗？这些问题的答案，比语言本身的性能更重要。主流技术栈之所以主流，往往不是因为技术最优，而是因为生态最全、踩坑的人最多、解决方案最丰富。

## **8.4 忽略部署成本**

本地跑得爽，上线发现烧钱。这是很多新手的真实经历。数据库免费层不够用，AI API 按 token 计费，对象存储流量费高，服务器冷启动慢，CDN 收费复杂。你开发时觉得“反正是免费层”，上线后账单来了才发现问题。

避坑建议：项目早期就用免费层或低成本方案。Vercel、Netlify、Cloudflare Pages 免费部署前端。Supabase、Neon、Railway、Render 提供免费或低价数据库和后端。SQLite 本地零成本。AI API 先用小模型或免费额度，设置用量上限。对象存储用 Cloudflare R2，流量便宜。做之前算一笔账：数据库、存储、流量、API、域名、SSL，每月大概多少。如果超过预算，换方案。

## **8.5 AI 生成代码不审查**

这是 vibe coding 新手最容易犯的错。AI 生成代码看起来完整、能跑，就直接复制到项目里。结果可能有：安全漏洞、密钥硬编码、依赖版本冲突、过时 API、逻辑错误、性能问题、许可证问题。AI 不是不会犯错，而是犯错时看起来很自信。

避坑建议：AI 生成的代码必须审查。重点看：有没有硬编码密钥？有没有 SQL 注入风险？有没有 XSS？依赖版本是否兼容？API 是否过时？逻辑是否符合需求？有没有异常处理？涉及钱、权限、用户数据的地方，尤其要小心。审查不是不信任 AI，而是对自己项目负责。另外，让 AI 写测试，跑一遍，比肉眼看更可靠。

## **8.6 低估学习曲线**

新手容易低估一些技术的学习难度。Rust 的所有权和生命周期、Kubernetes 的概念和配置、分布式系统的一致性和容错、函数式编程的抽象、Spring Boot 的生态和配置，这些都不是一周能掌握的。你看到别人用得很溜，是因为别人已经踩过坑。你从零开始，需要时间。

避坑建议：先学能出成果的。先做能上线的。先掌握一个能跑通全流程的技术栈，再逐步深入。不要一上来就挑战最难的。如果你想学 Rust，先用 Python 或 TypeScript 做出项目，再学 Rust 作为进阶。如果你想学 Kubernetes，先用托管平台部署，理解基本概念后再自建。学习曲线陡的技术，适合有基础、有时间、有明确目标的人。

## **8.7 什么都想学**

前端、后端、移动、桌面、AI、区块链、游戏，什么都想学。结果是每个都学一点，每个都不精。做项目时，哪个都不够用。这是新手常见的焦虑：怕错过，怕落后，怕选错方向。

避坑建议：先深后广。用一个完整项目打通一条链路。比如做 Web 全栈，从数据库到前端到部署，全部自己走一遍。做完一个，你会对技术栈有整体认知，再学其他会快很多。不要同时开五个方向。专注一个，做出成果，再扩展。技术是学不完的，但核心思维和工程能力是通用的。

## **8.8 只看教程不写项目**

看十遍教程，不如做一遍项目。新手容易陷入“教程地狱”：看完一个又看下一个，感觉都懂了，但自己写就卡住。因为教程是别人整理好的，问题是预设的，路径是清晰的。真实项目没有教程，你需要自己拆解问题、查文档、调试、做决策。

避坑建议：每学一个点，就做一个小 demo。学完 React，做一个待办列表。学完 FastAPI，做一个短链接服务。学完数据库，做一个记账工具。学完部署，把 demo 上线。做项目会遇到真实问题：依赖冲突、环境差异、部署失败、性能瓶颈。这些问题才是真正让你成长的。不要等“学完”再做，永远没有学完的时候。

## **8.9 忽略安全**

新手往往认为安全是以后的事，先做出功能再说。但安全漏洞一旦上线，可能造成真实损失：用户密码泄露、数据库被删、API 被刷、服务器被挖矿。常见漏洞包括：SQL 注入、XSS、CSRF、密钥泄漏、权限越权、文件上传漏洞、依赖漏洞。

避坑建议：用成熟框架的认证和授权，不要自己造。密钥放环境变量，不要提交到 Git。用户输入必须校验，SQL 用参数化查询，前端输出要转义。API 要做鉴权、限流、日志。依赖定期更新，用 `npm audit`、`pip audit` 检查。涉及用户数据，了解基本隐私法规。安全不是一次性的，是持续的过程。

## **8.10 忽略数据库选择**

数据库选错，后期迁移非常痛苦。常见错误：关系型数据用 NoSQL，后期查询复杂；小工具上重型数据库，部署麻烦；大数据用 SQLite，并发崩溃；AI 检索用传统数据库，性能差。新手往往因为“MongoDB 灵活”或“Redis 快”就选，忽略实际需求。

避坑建议：不确定就选 PostgreSQL。它能覆盖关系型、JSON、全文搜索、向量检索，一个数据库解决大部分需求。本地小工具选 SQLite。缓存选 Redis。AI 检索选 pgvector 或 Chroma。NoSQL 只在确实需要灵活结构或高吞吐写入时用。选数据库时问自己：数据结构固定吗？需要事务吗？查询复杂吗？数据量多大？并发多高？未来要迁移吗？

## **8.11 过早优化**

还没用户就优化性能，还没流量就考虑分布式，还没数据就做缓存。新手容易陷入“性能焦虑”，觉得必须用最快的语言、最优的架构。结果复杂度上去了，开发速度下来了，用户却没几个。

避坑建议：先跑通，再优化。先上线，再完美。性能问题等有数据再说。用监控工具看真实瓶颈：是数据库慢？是 API 慢？是前端大？是网络延迟？针对瓶颈优化，不要凭感觉。大多数项目，PostgreSQL + Node.js / Python 完全够用。真到瓶颈了，加缓存、加索引、加机器，比重构架构简单得多。

## **8.12 不写文档和测试**

三个月后自己都看不懂代码，改一个功能崩三个地方。新人接手项目，问你这块怎么跑，你答不上来。这不是能力问题，是习惯问题。文档和测试看起来费时间，但长期省时间。

避坑建议：README 写清楚项目是什么、怎么装、怎么跑、怎么部署、环境变量有哪些。关键逻辑写注释，复杂决策写文档。核心功能写测试，尤其是涉及钱、权限、数据的部分。提交信息写明白，不要一堆“update”。用 Git 分支管理，不要直接在主分支乱改。文档和测试不需要完美，但要有。它们是给未来的自己和别人看的。

## **8.13 锁定厂商**

深度绑定某个平台，想迁移时发现数据拿不出来。比如用了某云厂商的专有数据库、专有函数、专有存储，业务逻辑写在平台服务里，迁移成本极高。新手容易被“一站式”“全托管”吸引，忽略锁定风险。

避坑建议：核心数据可导出。尽量用开源标准，比如 PostgreSQL、S3 兼容存储、Docker。业务逻辑尽量放在自己代码里，不要全写在平台专有服务里。用托管服务可以，但要留后路。选平台时问自己：数据能导出吗？代码能迁移吗？API 是标准的吗？如果哪天要换，成本多大？

## **8.14 忽略合规**

隐私政策、用户数据、版权、许可证、备案，这些看起来和法律相关，但技术选型时就要考虑。比如你做国内 Web 服务，需要 ICP 备案；你收集用户数据，需要隐私政策；你用人脸识别，需要合规资质；你用开源库，要注意许可证是否允许商用。

避坑建议：提前了解目标市场的法规。国内做网站，先备案。收集用户数据，写隐私政策，最小化收集。用开源库，看许可证（MIT、Apache 2.0 通常安全，GPL 有传染性）。做支付、医疗、金融，了解行业资质。合规不是上线后才想的事，选型时就该纳入考虑。

## **8.15 不备份**

数据库丢失、代码丢失、配置丢失，这些事故一旦发生，可能无法挽回。新手往往觉得“不会那么倒霉”，直到真的发生。服务器被删、误操作、硬盘故障、勒索软件，都是真实风险。

避坑建议：代码放 GitHub / GitLab，定期提交。数据库自动备份，至少每天一次，备份存不同地方。重要配置文档化，不要只存在脑子里。环境变量有模板文件（`.env.example`）。关键数据导出存档。备份要测试恢复，否则备份等于没有。花几十块钱买云存储，比数据丢失后痛哭强。

## **8.16 不记录决策**

为什么选这个框架？为什么不选那个数据库？当时考虑了什么？三个月后你全忘了。别人问你，你也答不上来。想调整时，不知道当初的约束是什么。

避坑建议：写一个 `docs/tech-stack.md`，记录：选了什么、为什么选、替代方案是什么、风险是什么、未来可能怎么调整。每次重大决策都记录。这个文档以后会帮到你，也会帮到接手的人。决策记录不需要长，几句话就行，但要有。

## **8.17 不设边界**

项目范围无限扩大，功能越加越多，技术栈越换越乱。今天想加 AI，明天想加社交，后天想加电商。结果什么都没做完。新手容易兴奋，看到什么功能都想加。

避坑建议：明确 MVP。最小可用版本只做核心功能。其他功能列 backlog，上线后再说。技术栈也设边界：这个项目只用这套，新东西开新项目。不要在一个项目里试所有技术。做完一个，再做下一个。完成比完美重要。

## **8.18 本章小结**

避坑清单看起来长，但核心就几条：不要过度设计，不要盲目追新，不要忽略生态、部署、安全、备份、合规。用主流技术，做最小验证，先跑通再优化，先上线再完美。AI 可以加速，但要审查。文档和测试要有。决策要记录。边界要清晰。

每次选型时，对照这一章过一遍。不需要全部避免，但要知道它们存在。踩坑不可怕，可怕的是踩了不知道，下次还踩。技术栈选择是动态过程，随着项目成长不断调整。保持学习，保持谨慎，保持行动。
