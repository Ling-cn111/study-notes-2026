# **第二章 主流产品形态**

选技术栈的第一步，不是选语言，也不是选框架，而是先搞清楚你要做的东西到底属于哪种产品形态。产品形态决定了用户怎么接触你的产品，也决定了你后面一系列技术选择的方向。同样是做一个“记账工具”，做成网页、手机 App、微信小程序还是桌面软件，背后的技术栈可能完全不同。很多新手一上来就问“我该学 React 还是 Vue”，其实这个问题问早了。你应该先问：“我要做的东西，用户在哪里用？”

这一章会把常见的产品形态逐一拆开讲。每种形态我都会说清楚它是什么、适合什么场景、新手好不好上手、大致的技术栈方向，以及最容易踩的坑。你读完这一章，应该能对自己的项目有一个基本定位。

## **2.1 Web 应用**

Web 应用是目前最主流、对新手最友好的产品形态。简单说，就是用户通过浏览器访问的网站或网页系统。它不需要安装，输入网址就能用，电脑手机都能打开，更新也方便——你改了代码，用户刷新一下就看到了。这种“无需安装、跨平台、即时更新”的特点，让 Web 成为绝大多数项目的首选形态。

Web 应用的典型场景非常多。企业官网、个人博客、后台管理系统、在线文档、电商平台、社交社区、SaaS 工具、在线教育、数据看板，全都属于 Web 应用。可以说，只要你打开浏览器使用的服务，基本都是 Web 应用。

对新手来说，Web 的友好程度是最高的。原因有几个。第一，入门门槛低。你只需要一个浏览器和一个编辑器就能开始写代码，不需要配置复杂的开发环境。第二，反馈快。改一行代码，浏览器刷新就能看到效果。第三，生态成熟。无论是前端还是后端，Web 领域的教程、文档、社区问答都是最丰富的，AI 对 Web 技术栈也最熟悉，生成的代码质量相对最高。第四，部署便宜甚至免费。Vercel、Netlify、Cloudflare Pages 这些平台可以让你免费部署前端，Supabase、Railway、Render 提供免费或低价的数据库和后端托管。

Web 应用的技术栈方向大致分为前端、后端、数据库、部署四块。前端最主流的是 React、Vue、Svelte，配合 TypeScript 和 Tailwind CSS。后端选择很多，Node.js（Express / NestJS）、Python（FastAPI / Django）、Go（Gin）、PHP（Laravel）、Java（Spring Boot）都可以。数据库常用 PostgreSQL、MySQL，小项目用 SQLite 也很合适。部署方面，前端可以放 Vercel 或 Netlify，后端可以放 Railway、Render 或云服务器。

新手做 Web 应用，最常见的坑是“想太多”。比如一上来就纠结用不用微服务、要不要上 Redis、要不要做 SSR、要不要用 GraphQL。其实一个普通的 Web 项目，用 Next.js + PostgreSQL + Vercel 就能覆盖大部分需求。等真正遇到性能瓶颈或业务复杂度上升，再考虑引入更多技术。另一个坑是“前后端分离焦虑”。新手容易觉得必须前后端完全分离才专业，其实 Next.js、Nuxt 这类全栈框架已经把前后端整合得很好，写起来更省心。

如果你完全不知道从哪开始，我的建议是：TypeScript + Next.js + Tailwind CSS + PostgreSQL + Vercel。这套组合学习曲线平缓，生态极大，AI 支持最好，部署几乎零成本，能覆盖从博客到 SaaS 的大部分场景。等你做了一两个项目，再根据需求调整。

## **2.2 移动应用**

移动应用指的是安装在手机上的 App，比如微信、抖音、美团、小红书。它和 Web 的最大区别是：需要下载安装，能调用手机硬件（摄像头、定位、通讯录、推送），体验更流畅，但开发和维护成本更高。

移动应用的典型场景包括社交、电商、工具、健康、教育、出行、金融等。凡是需要高频使用、依赖手机硬件、追求原生体验的产品，通常都会做 App。比如拍照修图、跑步记录、即时通讯、移动支付，这些用 Web 做体验会差很多。

对新手来说，移动应用的友好程度是中等。它比 Web 难，但也没有想象中那么可怕。难点主要在于：你需要理解移动端的交互习惯、屏幕适配、权限管理、应用商店审核、版本发布流程。而且移动端调试比 Web 麻烦，真机测试、模拟器配置、签名证书这些概念，新手第一次接触会有点懵。

移动应用的技术栈方向分三条路。第一条是原生开发：iOS 用 Swift + SwiftUI，Android 用 Kotlin + Jetpack Compose。原生开发的优点是性能最好、体验最流畅、能用到所有系统能力；缺点是只覆盖一个平台，想同时做 iOS 和 Android 就得写两套代码，学习成本翻倍。第二条是跨平台开发：React Native 和 Flutter。React Native 用 JavaScript / TypeScript，Flutter 用 Dart。它们能用一套代码同时跑在 iOS 和 Android 上，开发效率高，生态也不错。第三条是混合开发：用 Web 技术套一个原生壳，比如 Cordova、Capacitor。这种方式适合内容展示型 App，但性能和体验一般。

新手做移动应用，最常见的坑是“低估审核和发布”。你以为写完代码就完了？不是。App Store 和 Google Play 有严格的审核规则，隐私政策、权限说明、截图、描述、年龄分级，一样不能少。国内安卓市场更是碎片化，各家应用商店规则不同。另一个坑是“盲目选原生”。如果你只是做一个内容展示或简单工具，跨平台完全够用，没必要写两套原生代码。反过来，如果你要做高性能游戏或深度硬件交互，跨平台可能撑不住，那就得原生。

如果你是新手上路，想做移动 App，我建议先用 React Native 或 Flutter 做跨平台。React Native 适合有前端基础的人，Flutter 适合愿意学 Dart、追求 UI 一致性的人。后端可以复用 Web 那一套，比如 Supabase、Firebase 或 FastAPI。等产品验证成功、有明确性能需求，再考虑原生重构。

## **2.3 桌面应用**

桌面应用是安装在电脑上的软件，比如 VS Code、Figma、Notion、微信桌面版、Photoshop。它的特点是性能强、可以离线、能访问本地文件、适合复杂操作。缺点是安装麻烦、更新需要用户配合、跨平台适配成本高。

桌面应用的典型场景包括：开发工具、设计软件、音视频编辑、办公软件、企业内部系统、数据分析工具、游戏。凡是需要大量计算、本地文件操作、多窗口、快捷键、离线使用的场景，桌面应用都比 Web 更合适。

对新手来说，桌面应用的友好程度是中等偏下。它比 Web 和移动都小众，教程和社区相对少，调试和打包也更复杂。不过，近几年 Electron 和 Tauri 的出现，让前端开发者也能做桌面应用，门槛降低了不少。

桌面应用的技术栈方向主要有四条。第一条是 Electron：用 HTML / CSS / JavaScript 写界面，套一个 Chromium 和 Node.js 的壳。VS Code、Slack、Discord 都是 Electron 做的。优点是前端技术直接复用，生态极大；缺点是体积大、内存占用高。第二条是 Tauri：前端写界面，后端用 Rust，打包体积小、性能好、更安全。缺点是 Rust 有学习曲线，生态还不如 Electron 成熟。第三条是原生开发：Windows 用 C# + WPF / WinUI，macOS 用 Swift + SwiftUI，Linux 用 Qt / GTK。原生性能最好，但跨平台成本高。第四条是跨平台框架：Qt、.NET MAUI、Flutter Desktop。Qt 成熟但学习曲线陡，.NET MAUI 适合 C# 生态，Flutter Desktop 还在发展中。

新手做桌面应用，最常见的坑是“忽略打包和签名”。写代码只是第一步，打包成安装包、做代码签名、处理自动更新，这些才是真正麻烦的地方。Windows 和 macOS 的签名规则不同，macOS 还要求公证，否则用户打开会报安全警告。另一个坑是“用 Electron 做一切”。Electron 很方便，但内存占用大、启动慢，如果只是做一个小工具，Tauri 可能更合适。

如果你有前端基础，想做桌面应用，我建议先试 Electron，因为学习成本最低，资料最多。如果你在意体积和性能，愿意学一点 Rust，可以试 Tauri。如果你做的是 Windows 企业内部工具，C# + WPF 也是很稳的选择。

## **2.4 小程序**

小程序是运行在超级 App 里的轻量应用，最典型的是微信小程序，此外还有支付宝小程序、抖音小程序、百度小程序等。它的特点是免安装、即用即走、依赖平台流量、开发相对简单。用户扫个码或搜一下就能用，不用去应用商店下载。

小程序的典型场景包括：电商、点餐、预约、票务、活动报名、轻工具、企业展示、会员系统。凡是想快速触达用户、依赖社交传播、功能不太复杂的场景，小程序都很合适。特别是微信小程序，依托微信的社交关系链和支付能力，做电商和本地生活服务非常方便。

对新手来说，小程序的友好程度是比较高的。它的开发语法接近 Web，学过 HTML / CSS / JavaScript 的人上手很快。微信开发者工具也很完善，调试、预览、上传、审核一条龙。而且小程序不需要处理 iOS / Android 适配，平台帮你屏蔽了很多底层细节。

小程序的技术栈方向主要有三种。第一种是原生小程序：微信用自己的 WXML、WXSS、JS，支付宝、抖音也各有各的语法。优点是性能最好、平台支持最全；缺点是不能跨平台，换一个平台就得重写。第二种是跨端框架：Taro 和 uni-app。它们支持用 React 或 Vue 的语法写小程序，还能同时编译到微信、支付宝、抖音、H5、App 等多个平台。优点是效率高、代码复用；缺点是某些平台特有能力可能支持不完全。第三种是云开发：微信云开发、支付宝云开发，直接提供数据库、存储、云函数，不用自己搭后端。优点是极简、快；缺点是绑定平台、迁移困难。

新手做小程序，最常见的坑是“忽略平台限制”。小程序不是网页，它有很多限制：包体积不能超过 2MB（分包后总大小也有限制）、不能随意跳转外部链接、不能直接操作 DOM、审核规则严格、类目需要资质。比如你做电商，可能需要营业执照；做医疗、金融，资质要求更高。另一个坑是“低估审核时间”。小程序提交审核后，可能要等几小时到几天，遇到节假日更久。如果你赶时间上线，一定要提前规划。

如果你是新手上路，想做小程序，我建议先用微信原生或 uni-app。微信原生最直接，文档最全；uni-app 适合想跨平台的人。后端可以用云开发，也可以用 Web 那一套。先做一个简单功能跑通审核流程，再逐步加功能。

## **2.5 API 服务**

API 服务是一种“没有界面”的产品形态。它不直接面向普通用户，而是提供接口，让其他程序来调用。比如你做一个天气 API，前端 App 调用它获取天气数据；你做一个支付 API，电商网站调用它完成收款；你做一个 AI API，聊天机器人调用它生成回复。API 服务的核心是“数据”和“能力”，而不是“页面”。

API 服务的典型场景包括：后端服务、微服务、数据接口、AI 模型服务、第三方开放平台、内部系统对接。现在很多产品都是前后端分离的，前端负责界面，后端就是 API 服务。你看到的网页、App、小程序，背后往往都有一个或多个 API 服务在支撑。

对新手来说，API 服务的友好程度是比较高的。它不需要你懂 CSS、响应式布局、浏览器兼容，只需要专注逻辑、数据、性能、安全。而且 API 的调试工具很成熟，Postman、Insomnia、curl、Swagger 都能帮你测试。AI 对 API 代码也很熟悉，生成质量通常不错。

API 服务的技术栈方向非常丰富。Python 有 FastAPI、Flask、Django REST Framework；Node.js 有 Express、NestJS、Fastify；Go 有 Gin、Echo、Fiber；Java 有 Spring Boot；PHP 有 Laravel；Ruby 有 Rails。数据库根据需求选，关系型用 PostgreSQL / MySQL，缓存用 Redis，文档型用 MongoDB，向量检索用 pgvector / Chroma。部署可以放云服务器、容器平台、Serverless 函数。

新手做 API 服务，最常见的坑是“忽略接口设计”。很多人一上来就写代码，结果接口命名混乱、错误码不统一、版本没规划、鉴权不清晰。好的 API 设计应该考虑：URL 语义化、HTTP 方法正确使用、统一错误格式、分页、过滤、排序、版本控制、鉴权、限流、日志。另一个坑是“忽略安全”。API 直接暴露在公网，容易被扫描、攻击、刷接口。你需要做：HTTPS、身份验证、权限控制、输入校验、速率限制、敏感数据脱敏。

如果你是新手上路，想做 API 服务，我建议用 Python + FastAPI 或 Node.js + Express。FastAPI 自带文档、类型提示、异步支持，非常适合新手和 AI 协作。Express 更轻量，生态更大。先做一个简单的 CRUD API，跑通部署和调用，再考虑复杂功能。

## **2.6 AI 应用**

AI 应用是近几年最热的产品形态。它通常指集成大语言模型、向量检索、图像生成、语音识别等 AI 能力的应用。比如聊天机器人、知识库问答、文档总结、AI 写作、AI 绘图、智能客服、代码助手，都属于 AI 应用。AI 应用的核心是“模型能力 + 业务场景 + 数据”。

AI 应用的典型场景包括：企业知识库、教育辅导、内容生成、客服自动化、数据分析、科研辅助、个人助手。几乎每个行业都在尝试用 AI 重构产品或流程。对新手来说，AI 应用是一个很好的切入点，因为大模型 API 已经非常成熟，你不需要自己训练模型，只需要调用接口、设计提示词、组织数据。

对新手来说，AI 应用的友好程度是比较高的，但变化快。友好是因为：Python 生态强大，LangChain、LlamaIndex 等框架降低了开发难度，OpenAI、Anthropic、国内大模型都提供简单易用的 API。变化快是因为：模型迭代频繁、框架更新快、最佳实践不断演变，今天能用的方法明天可能就过时了。

AI 应用的技术栈方向大致分四层。第一层是模型层：可以用 OpenAI API、Claude API、Gemini API，也可以用开源模型如 Llama、Qwen、DeepSeek，本地部署或云托管。第二层是编排层：LangChain、LlamaIndex、Haystack，负责连接模型、工具、数据、记忆。第三层是数据层：向量数据库（pgvector、Chroma、Pinecone、Weaviate）、文档加载器、嵌入模型。第四层是应用层：前端用 Next.js / React，后端用 FastAPI / Node.js，部署用 Vercel / Railway / 云服务器。

新手做 AI 应用，最常见的坑是“忽略成本和延迟”。大模型 API 按 token 收费，用多了很贵；本地模型需要 GPU，成本也不低。而且模型推理有延迟，用户等待时间可能很长。另一个坑是“忽略幻觉和准确性”。大模型会编造信息，尤其是在知识库问答中，如果没有好的检索和提示词设计，答案可能完全错误。还有一个坑是“忽略隐私和安全”。用户数据发给第三方 API 时，要确认对方的数据使用政策；API 密钥不能泄露；敏感数据要考虑脱敏或本地部署。

如果你是新手上路，想做 AI 应用，我建议从最简单的开始：Python + FastAPI + OpenAI API（或国内模型）+ 一个前端页面。先做一个聊天机器人或文档问答，跑通流程，理解 token、提示词、上下文、嵌入、检索这些概念。然后再引入 LangChain 或 LlamaIndex，做更复杂的 RAG 或 Agent。向量库先用 pgvector 或 Chroma，简单够用。等规模上来，再考虑专业向量数据库。

## **2.7 浏览器扩展**

浏览器扩展是安装在 Chrome、Edge、Firefox 等浏览器上的小插件，用来增强网页功能。比如广告拦截、翻译、笔记、密码管理、网页截图、价格比较。它的特点是轻量、贴近浏览器、能修改网页内容、开发门槛低。

浏览器扩展的典型场景包括：效率工具、网页增强、内容采集、隐私保护、开发者工具、购物辅助。凡是需要在浏览网页时提供额外功能的场景，都适合做扩展。比如你做一个“一键保存网页到笔记”的扩展，或者“自动填写表单”的扩展，都很实用。

对新手来说，浏览器扩展的友好程度是比较高的。它本质上就是 HTML / CSS / JavaScript，加上一些浏览器提供的 API。你不需要学新语言，只要懂前端基础，就能做出一个可用的扩展。而且 Chrome 网上应用店发布流程相对简单，费用也不高。

浏览器扩展的技术栈方向比较集中。核心是 HTML / CSS / JavaScript / TypeScript，加上 Chrome Extensions API（Manifest V3）。你也可以用 React、Vue、Svelte 来写扩展的界面，但扩展本身通常不大，用原生 JS 也够。构建工具可以用 Vite、Webpack、Parcel。状态管理、路由这些，看复杂度决定。

新手做浏览器扩展，最常见的坑是“权限申请过多”。扩展需要声明权限，比如访问所有网站、读取浏览记录、修改页面内容。权限越多，审核越严，用户越不信任。你应该遵循最小权限原则，只申请必要的权限。另一个坑是“忽略 Manifest V3 的变化”。Chrome 已经从 Manifest V2 迁移到 V3，背景页、网络请求、远程代码等规则都变了。如果你看的是老教程，可能会踩坑。还有一个坑是“不测试多浏览器”。Chrome、Edge、Firefox 的扩展 API 有差异，想跨浏览器发布，需要做兼容。

如果你是新手上路，想做浏览器扩展，我建议先用原生 JavaScript + Manifest V3 做一个简单扩展，比如“一键复制网页标题和链接”。跑通开发、调试、打包、发布流程，再考虑复杂功能。界面可以用 React 或 Vue，但不要一开始就上重型框架。

## **2.8 自动化脚本**

自动化脚本是用代码自动完成重复性任务的程序。它通常没有界面，或者只有一个简单的命令行界面。比如批量重命名文件、定时抓取网页数据、自动填写 Excel、批量压缩图片、监控网站变化、自动发送邮件。自动化脚本的特点是：小、快、实用、解决具体问题。

自动化脚本的典型场景包括：文件处理、数据清洗、爬虫、定时任务、系统运维、报表生成、消息推送、测试自动化。几乎每个行业都有大量重复劳动，自动化脚本可以帮你节省大量时间。对新手来说，这是最容易获得成就感的产品形态。

对新手来说，自动化脚本的友好程度是最高的。你不需要考虑界面、部署、用户管理，只需要专注逻辑。Python 是自动化脚本的首选语言，语法简单，库极其丰富。你写十几行代码，就能完成一个实用工具。而且调试简单，跑一遍看结果就行。

自动化脚本的技术栈方向主要是 Python 和 Node.js。Python 有 requests、BeautifulSoup、Scrapy、pandas、openpyxl、Playwright、Selenium、schedule、APScheduler。Node.js 有 Puppeteer、Playwright、axios、cheerio。Shell 和 PowerShell 也常用于系统级自动化。如果涉及定时执行，可以用 cron、GitHub Actions、云函数。

新手做自动化脚本，最常见的坑是“忽略法律和道德”。爬虫不能违反目标网站的 robots.txt，不能抓取个人隐私数据，不能高频请求导致对方服务器瘫痪。另一个坑是“忽略异常处理”。脚本跑一次成功不代表一直成功，网络会断、页面会变、文件会丢。你需要加错误处理、重试、日志、通知。还有一个坑是“硬编码路径和密钥”。脚本换一台电脑就跑不了，或者密钥泄露。应该用配置文件、环境变量、相对路径。

如果你是新手上路，想做自动化脚本，我建议从 Python 开始。先写一个简单的文件整理脚本，再写一个网页抓取脚本，再写一个定时任务。每完成一个，你都会对编程更有信心。自动化脚本是新手最好的练手项目，也是理解编程思维的最佳途径。

## **2.9 如何判断你的项目属于哪种形态**

读完上面八种形态，你可能已经对号入座了。但有些项目是混合的，比如一个产品既有 Web 端，又有移动 App，还有小程序。这很正常。你不需要一次做完所有形态，而是先选一个最主要的、最能验证核心价值的形态。

判断方法可以问自己几个问题。用户主要在哪里使用？如果是电脑浏览器，选 Web；如果是手机，选移动或小程序；如果是电脑桌面，选桌面应用；如果是其他程序调用，选 API；如果核心是 AI 能力，选 AI 应用；如果是在浏览网页时辅助，选扩展；如果是自己或团队内部用，选脚本。

哪个形态能最快做出最小可用版本？新手应该优先选开发速度快、部署成本低、反馈周期短的形态。通常 Web 和脚本最快，移动和桌面较慢，小程序中等，AI 应用取决于模型调用。

你的团队擅长什么？如果只有你一个人，选你熟悉或容易学的。如果有前端，Web 和扩展容易；如果有 Python，API 和 AI 容易；如果有移动开发，App 容易。

未来要不要扩展？有些项目先做 Web，再打包成桌面；先做小程序，再扩到 App；先做脚本，再包装成 API。技术栈选择要考虑未来迁移成本。比如用 React 做 Web，以后可以用 React Native 做移动；用 Next.js 做 Web，以后可以用 Tauri 做桌面。

## **2.10 本章小结**

产品形态是技术栈选择的第一层决策。Web 应用最通用、最适合新手；移动应用体验好但成本高；桌面应用性能强但分发麻烦；小程序流量大但受平台限制；API 服务是后端核心；AI 应用热门但变化快；浏览器扩展轻量实用；自动化脚本最简单直接。

新手最稳的路径是：从 Web 应用或自动化脚本开始，用主流技术栈做出最小可用版本，跑通上线流程，再根据需求扩展到其他形态。不要一上来就做全平台，不要为了“看起来专业”选复杂形态。先做一个能用的东西，比什么都重要。

下一章我们讲“主流编程语言”，会逐一分析 JavaScript / TypeScript、Python、Java、Go、Rust、C#、Kotlin、Swift、PHP、Ruby 的特点、优势、局限、典型用途、学习曲线和 AI 友好度。你会看到，语言没有绝对好坏，只有适不适合你的场景。
