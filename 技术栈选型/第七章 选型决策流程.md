# **第七章 选型决策流程**

前面六章讲了产品形态、语言、框架、数据库、对比表，信息量已经很大。但真正做项目时，你可能还是不知道从哪下手。这一章给你一套可操作的流程，从项目目标开始，一步步缩小范围，最终锁定一套技术栈。流程不复杂，但每一步都很关键。照着走，你不会选出完美方案，但能避开大多数坑。

## **7.1 第一步：明确项目目标**

技术栈是手段，不是目的。选型之前，你必须先回答一个问题：这个项目到底要干什么？目标不同，技术栈完全不同。

如果项目是为了学习，优先选生态大、资料多、就业好的技术。比如 TypeScript + React + Node.js，学完能迁移到很多场景。如果项目是为了快速验证商业想法，优先选开发快、部署便宜、能快速上线的技术。比如 Next.js + Supabase + Vercel。如果项目是为了长期维护的企业系统，优先选稳定、成熟、可招聘的技术。比如 Java + Spring Boot + PostgreSQL。如果项目只是个人工具，优先选你最熟悉、最省事的技术。比如 Python + SQLite。如果项目是作品集，优先选能展示你能力、看起来专业的技术。比如 Next.js + TypeScript + PostgreSQL + Docker。

目标不明确，选型就会摇摆。今天看别人用 Go，明天看别人用 Rust，最后什么都没做成。所以，先写下你的项目目标，越具体越好。

## **7.2 第二步：确定产品形态**

目标明确后，确定产品形态。用户在哪里用？浏览器、手机、桌面、小程序、命令行，还是其他程序调用？产品形态决定了技术栈的大方向。

如果用户主要用浏览器，选 Web。如果用户主要在手机，选移动或小程序。如果用户主要在电脑桌面，选桌面。如果其他程序调用你的服务，选 API。如果核心是 AI 能力，选 AI 应用。如果是在浏览网页时辅助，选扩展。如果是自己或团队内部用，选脚本。

有些项目是混合形态，比如 Web + 移动 + 小程序。新手不要一次做所有形态。先选一个最主要的、最能验证核心价值的形态。比如先做 Web，验证后再做移动；先做小程序，验证后再扩 App。技术栈选择要考虑未来迁移，但不要为未来过度设计。

## **7.3 第三步：评估团队能力**

团队能力是选型中最容易被忽略、却最影响成败的因素。一个人做项目和十个人做项目，选型逻辑完全不同。

如果只有你一个人，选你熟悉或容易学的技术。不要选需要多人协作才发挥优势的重型框架，比如 Spring Boot + 微服务。一个人做全栈，Next.js + Supabase 是最快路径。如果你有前端，可以前端 React，后端 Node.js 或 Python。如果你有后端，可以后端 FastAPI 或 Spring Boot，前端 Vue 或 React。如果团队都是 Java 背景，硬上 Node.js 会痛苦。如果团队都是 Python 背景，硬上 Go 也会痛苦。

团队能力还包括学习意愿和时间。如果大家愿意学，可以引入新技术，但要留出学习时间。如果时间紧，用团队熟悉的。不要为了“技术升级”牺牲交付。

## **7.4 第四步：评估时间预算**

时间预算决定你能选多复杂的技术栈。一周出原型和三个月做产品，选型完全不同。

一周出原型：选 BaaS + 现成 UI 库 + 托管部署。比如 Next.js + Supabase + Vercel + shadcn/ui。不要自己搭后端，不要自己配服务器，不要选需要长时间学习的技术。一个月做 MVP：选主流全栈框架 + 托管数据库 + 云部署。比如 Next.js + PostgreSQL + Railway。可以写一些自定义后端逻辑，但仍以快为主。三个月做产品：可以引入更多技术，比如 Redis、队列、对象存储、CI/CD、测试。但仍要避免过度设计。半年以上长期项目：重视可维护性、可测试性、可扩展性。可以引入 Docker、监控、日志、自动化测试、代码审查。

时间越紧，越要选成熟、托管、少配置的技术。时间越宽，越可以选需要学习但长期收益大的技术。

## **7.5 第五步：评估性能需求**

性能需求决定语言和架构。但新手最容易高估性能需求。大多数项目，用户不到一万，PostgreSQL + Node.js / Python 完全够用。不要还没用户就考虑分布式。

普通 CRUD：Node.js、Python、PHP、Ruby 都够。数据库 PostgreSQL / MySQL。高并发 API：Go、Java、Rust 更合适。数据库加 Redis 缓存，考虑读写分离。AI 推理：Python + GPU 或 API。向量检索用 pgvector / Chroma。实时通信：Node.js + WebSocket，或 Go + WebSocket。数据库 Redis 做发布订阅。大数据处理：Python + Spark，或 Go + 流处理。数据库选列式或 NoSQL。

性能需求要看真实数据，不要拍脑袋。先做最小版本，上线后看监控，有瓶颈再优化。过早优化是万恶之源。

## **7.6 第六步：评估部署环境**

部署环境影响技术栈选择。国内和海外、免费和付费、自建和托管，差别很大。

海外部署：Vercel、Netlify、Cloudflare Pages、Railway、Render、Fly.io、Supabase、Neon。免费层多，体验好，AI 友好。国内部署：阿里云、腾讯云、华为云、火山引擎。需要备案，访问速度快，但配置复杂，免费层少。混合部署：前端海外，后端国内，或反过来。注意网络延迟和数据合规。

预算低：优先免费层和托管服务。Vercel + Supabase + Railway 可以零成本起步。预算中等：云服务器 + Docker + 托管数据库。预算高：云厂商全套服务，CDN、负载均衡、监控、备份。

部署环境还要考虑：是否需要备案、是否需要 HTTPS、是否需要自定义域名、是否需要 CDN、是否需要对象存储、是否需要邮件服务、是否需要支付接口。这些都会影响技术栈。

## **7.7 第七步：评估可维护性**

项目上线后要维护几个月甚至几年。可维护性比开发速度更重要，但新手常常忽略。

可维护性包括：文档是否齐全、社区是否活跃、版本是否稳定、依赖是否健康、是否容易招聘、是否容易升级、是否容易测试、是否容易监控。

主流技术栈可维护性更好。React、Vue、Next.js、FastAPI、PostgreSQL 都有大量文档和社区支持。冷门框架可能开发时很爽，维护时很痛苦。依赖健康也很重要。一个库半年不更新、Issue 没人回，就要小心。版本稳定也关键。频繁破坏性更新的框架，升级成本高。容易招聘意味着你以后找人接手容易。容易测试和监控意味着你能快速发现问题。

选型时问自己：半年后我还能看懂这个项目吗？别人能接手吗？升级会痛苦吗？如果答案不确定，选更主流的。

## **7.8 第八步：评估 AI 协作友好度**

Vibe coding 时代，AI 协作友好度成为选型的重要维度。AI 友好度高，你写代码快、改 bug 快、学新东西快。AI 友好度低，AI 帮不上忙，甚至帮倒忙。

AI 友好度高的技术栈特征：主流语言（TypeScript、Python、Java、Go）、主流框架（React、Next.js、Vue、FastAPI、Django、Spring Boot）、类型强（TypeScript、Python 类型提示）、文档多、示例多、版本稳定、错误信息清晰、包管理成熟、社区活跃。

AI 友好度低的技术栈特征：过新框架、小众库、文档少、频繁破坏性更新、类型弱、配置复杂、错误信息晦涩。

选型时问自己：AI 能帮我写这个吗？AI 生成的代码我能审查吗？遇到问题 AI 能解释吗？如果 AI 不熟悉，你要花更多时间自己解决。

## **7.9 第九步：先选默认栈，再做最小验证**

走完前八步，你应该有几个候选方案。如果还在纠结，选默认栈。默认栈是经过大量项目验证的、适合大多数场景的组合。

Web 默认栈：TypeScript + Next.js + Tailwind CSS + PostgreSQL + Prisma + Vercel + Supabase Auth。AI 默认栈：Python + FastAPI + LangChain / LlamaIndex + pgvector + Next.js + Vercel。移动默认栈：TypeScript + React Native + Supabase。或 Dart + Flutter + Supabase。桌面默认栈：TypeScript + Electron + SQLite。脚本默认栈：Python + requests / pandas / Playwright。

选完默认栈后，做最小验证。只做登录 + 一个核心功能 + 部署。跑通再扩展。验证过程中，你会遇到真实问题：依赖冲突、部署失败、性能瓶颈、API 限制。这些问题会告诉你，选型是否需要调整。不要跳过验证直接开大项目。

## **7.10 第十步：锁定版本，记录决策**

验证通过后，锁定版本。Node、Python、依赖库、数据库、部署平台，都记录版本号。使用 lock 文件（package-lock.json、pnpm-lock.yaml、poetry.lock、requirements.txt）。版本锁定能避免“昨天还能跑，今天不行”的问题。

记录选型决策。写一个 `docs/tech-stack.md`，内容包括：为什么选这个语言、为什么选这个框架、为什么选这个数据库、替代方案是什么、风险是什么、未来可能怎么调整。这个文档以后会帮到你，也会帮到接手的人。

## **7.11 简化决策树**

如果上面的步骤太复杂，用下面这棵简化决策树。

只做网页？是 → Next.js + TypeScript + Tailwind + Supabase / PostgreSQL。否 → 继续。需要手机 App？是 → 跨平台选 React Native 或 Flutter；原生选 SwiftUI 或 Compose。否 → 继续。主要是 AI / 数据？是 → Python + FastAPI + LangChain / LlamaIndex + pgvector。否 → 继续。主要是企业后端？是 → Java Spring Boot 或 C# .NET + React。否 → 继续。只是自动化？是 → Python。否 → 回到 Web 默认栈。

这棵树覆盖大部分场景。如果还是不确定，选 Web 默认栈。它最通用，AI 最友好，学习资源最多。

## **7.12 本章小结**

选型决策流程可以总结成十步：明确目标、确定形态、评估团队、评估时间、评估性能、评估部署、评估可维护性、评估 AI 友好度、选默认栈做验证、锁定版本记录决策。

每一步都不需要完美，但每一步都要走。新手最容易跳过的是团队能力、时间预算、可维护性、AI 友好度。这四个恰恰是长期影响最大的。性能需求反而最容易被高估，大多数项目根本不需要高性能架构。

记住：技术栈是为你服务的，不是反过来。选你能驾驭的，选能快速上线的，选能长期维护的，选 AI 能帮上忙的。先跑通，再优化；先上线，再完美。
