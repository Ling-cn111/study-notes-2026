# **第九章 Vibe coding 选型建议**

Vibe coding 这个词，简单说就是“用 AI 辅助编程”。你描述需求，AI 生成代码，你审查、调试、迭代。它让写代码的门槛降低了很多，但也带来一个新问题：很多人以为有了 AI 就不需要懂技术选型了。恰恰相反，AI 越强，选型越重要。因为你选了一套主流、成熟、AI 熟悉的技术栈，AI 就是超级助手；你选了一套冷门、过时、文档稀少的技术栈，AI 可能比你还迷茫。这一章专门讲怎么和 AI 协作做技术选型，怎么描述需求，怎么验证 AI 建议，以及哪些技术栈更适合 AI 编程。

## **9.1 如何让 AI 帮你选技术栈**

很多人问 AI 的方式是：“我想做一个小程序，用什么技术栈？”这种问法太模糊，AI 只能给泛泛答案。好的提问应该包含背景、目标、约束和期望输出。你要让 AI 知道：你是谁、你要做什么、给谁用、有什么限制、你希望它怎么回答。

第一步，给 AI 一个角色。比如：“你是一位资深全栈工程师，擅长给新手推荐技术栈。”角色设定能让 AI 的回答更聚焦。第二步，给项目背景。一句话介绍项目，目标用户是谁，核心功能有哪些，产品形态是什么。第三步，给约束条件。你的技术背景、团队人数、时间预算、金钱预算、部署地区、偏好和禁忌。第四步，明确输出格式。比如：“请给我两套方案，每套包括前端、后端、数据库、部署、推荐理由、替代方案、风险提醒。”第五步，让 AI 对比。不要只让它给一套，让它给两到三套，并说明取舍。第六步，让 AI 说明“不推荐什么”。这往往比推荐更有价值，因为能帮你避开坑。

你还可以让 AI 反过来问你问题。比如：“在我推荐之前，请先问我五个问题，帮我澄清需求。”这样 AI 会先收集信息，再给建议，准确率更高。你也可以让 AI 生成决策树：“如果我要做 Web 应用，优先选什么；如果我要做移动 App，优先选什么。”决策树能帮你理解选型逻辑，而不是死记答案。

最后，不要只问一个 AI。不同 AI 的训练数据、知识截止时间、回答风格不同。你可以把同一个问题问两个 AI，对比它们的建议。如果两者都推荐同一套技术栈，那大概率是稳的。如果分歧很大，你要去看官方文档和社区，自己判断。

## **9.2 如何描述项目需求**

描述项目需求是 vibe coding 选型中最关键的一步。你给 AI 的信息越清楚，它给的答案越靠谱。下面这些信息，尽量都提供。

项目一句话描述。比如：“一个面向大学生的 AI 笔记管理 Web 应用，支持上传 PDF、自动总结、问答检索。”目标用户。比如：“大学生、自学者、研究人员。”核心功能。列出三到五个，不要太多。比如：“上传文档、自动摘要、知识库问答、标签管理、导出笔记。”产品形态。Web、移动、桌面、小程序、API、AI 应用、浏览器扩展、自动化脚本，选一个主要的。是否需要登录、支付、AI、实时通信。这些会直接影响技术栈。数据量级。小、中、大，大概多少用户、多少数据。团队情况。只有你一个人，还是两三个人；有没有前端、后端、设计。你的技术背景。会什么语言，不会什么，愿不愿意学新东西。时间预算。一周出原型，一个月 MVP，还是三个月产品。金钱预算。尽量免费，还是可以接受每月几十、几百。部署地区。国内、海外，还是不确定。偏好和禁忌。比如“不想学 Java”“希望 JS 全栈”“必须用微信生态”。成功标准。比如“能上线给同学用”“能写进简历”“能赚钱”。

你还应该写清楚“不要什么”。比如：“不要推荐微服务”“不要用 Rust，我没时间学”“不要绑定 Firebase，我想数据可导出”。负面约束能帮 AI 排除不合适选项。

一个完整的描述示例：“我想做一个个人博客，主要写技术文章，希望有 SEO，支持 Markdown，能评论，能订阅。我一个人做，会一点 HTML/CSS/JS，没写过后端。时间两周，预算尽量零。部署在海外，希望用免费平台。不要推荐 Java 和微服务，我希望简单、快、AI 友好。”有了这些信息，AI 就能给出非常具体的建议，比如 Next.js + MDX + Vercel + Supabase，而不是泛泛而谈。

## **9.3 如何验证 AI 建议**

AI 的建议不能全信。它可能过时，可能编造，可能忽略你的约束。你必须验证。验证的方法有很多，下面这些最实用。

第一，查官方文档。AI 推荐了一个框架，你去官网看它的入门教程、版本号、最近更新。如果官网文档很久没更新，或者版本号很乱，要警惕。第二，查 GitHub。看仓库的 Star 数、最近提交时间、Issue 回复速度、Pull Request 活跃度。如果半年没提交，Issue 没人回，说明维护不活跃。第三，查包管理平台。npm、PyPI、crates.io 上看下载量趋势、版本发布频率、依赖数量。下载量稳定增长是好事，突然下降或长期不动要小心。第四，让 AI 给最小 demo。比如：“请给我一个最小可运行示例，包括安装、启动、一个接口。”你亲自跑一遍。跑不通，说明有问题。第五，问 AI 风险。比如：“这套方案最大的三个风险是什么？”“如果我要迁移，成本高吗？”“有哪些隐藏成本？”第六，交叉验证。把同一问题问另一个 AI，看答案是否一致。第七，检查版本兼容。AI 可能推荐了 A 框架的最新版和 B 库的旧版，两者不兼容。你要看官方兼容性说明。第八，检查许可证。开源库的许可证是否允许商用，是否有传染性。第九，算部署成本。AI 说“免费”，你要看免费层限制：流量、存储、数据库大小、API 调用次数。第十，不要点 AI 给的链接。AI 可能编造链接，你要自己搜官方文档。

验证不是不信任 AI，而是对项目负责。AI 是助手，你是决策者。最终选什么，你承担后果。

## **9.4 适合 AI 编程的技术栈特征**

不是所有技术栈都适合 vibe coding。有些技术栈 AI 生成代码准确率高，你改起来快；有些技术栈 AI 经常写错，你修 bug 的时间比自己写还长。适合 AI 编程的技术栈通常有这些特征。

第一，主流语言和框架。TypeScript、Python、Java、Go、React、Vue、Next.js、FastAPI、Django、Spring Boot，这些语料多，AI 熟悉。第二，类型强。TypeScript、Python 类型提示、Java、Go、Rust 都有类型系统，AI 生成的代码更容易检查。第三，文档多、示例多。官方文档好，社区问答多，AI 训练数据里这类内容就多。第四，版本稳定。频繁破坏性更新的框架，AI 可能混用新旧 API，导致代码跑不通。第五，错误信息清晰。好的错误信息能帮你和 AI 快速定位问题。第六，包管理成熟。npm、pip、cargo、go mod 这些工具让依赖管理标准化。第七，社区活跃。遇到问题，搜索能找到答案，AI 也能参考。第八，单语言全栈。Next.js、Nuxt 这类框架前后端一体，AI 更容易理解上下文。第九，托管服务。Vercel、Supabase、Railway 这些平台部署简单，AI 能给出清晰步骤。第十，避免过新、小众、文档少、频繁破坏更新的技术。这些技术 AI 不熟，生成代码质量差。

具体来说，最 AI 友好的组合是：TypeScript + Next.js + Tailwind CSS + PostgreSQL + Prisma + Vercel。AI 应用是：Python + FastAPI + LangChain / LlamaIndex + pgvector + Next.js。移动是：TypeScript + React Native + Supabase，或 Dart + Flutter + Supabase。这些组合语料多、类型强、生态大、部署简单，AI 协作体验最好。

## **9.5 与 AI 协作时的注意事项**

和 AI 协作写代码，有一些坑要避开。第一，AI 可能过时。它的知识有截止时间，可能推荐已废弃的 API 或旧版本。你要让它注明版本，并去官方文档确认。第二，AI 可能编造。它会编造不存在的库、函数、参数、链接。你要验证每个关键 API。第三，不要贴密钥。API Key、数据库密码、用户数据，不要发给 AI。用占位符代替。第四，审查安全和依赖。AI 生成的代码可能有 SQL 注入、XSS、密钥硬编码、依赖漏洞。你要逐行审查，用工具扫描。第五，小步提交。不要一次让 AI 生成几千行，然后一起提交。分成小功能，每步测试，提交 Git，方便回滚。第六，让 AI 写测试和 README。测试能帮你验证代码，README 能帮你记住怎么跑。第七，遇到错误，先让 AI 解释原因，再改。不要盲目复制修复代码。第八，保持项目结构清晰。AI 需要上下文，结构乱它更容易出错。第九，不要一次生成太多。上下文窗口有限，太多代码 AI 会忘。第十，人工负责最终决策。AI 可以建议，但选型、架构、安全、合规，你要自己判断。

还有一个重要习惯：用版本控制。Git 是你的安全网。每次 AI 生成代码后，跑通再提交。出问题可以回滚。没有 Git，AI 改错代码，你可能找不回来。另外，让 AI 遵守项目规范。你可以告诉它：“本项目用 TypeScript 严格模式，函数用箭头函数，样式用 Tailwind，不要用 any。”这样生成的代码更一致。定期重构。AI 生成的代码可能重复、冗余、结构差。定期让 AI 帮你重构，保持代码健康。

## **9.6 一个实际例子**

假设你想做一个“AI 笔记管理 Web 应用”。你可以这样问 AI：

“你是一位资深全栈工程师。我想做一个面向大学生的 AI 笔记管理 Web 应用，支持上传 PDF、自动总结、知识库问答、标签管理。产品形态是 Web。需要登录，需要 AI，不需要支付。数据量初期小，几百用户。只有我一个人开发，会一点 Python 和 HTML/CSS/JS，没写过完整后端。时间一个月，预算尽量免费，部署海外。希望 AI 友好、数据可导出、不要微服务、不要 Java。请给我两套技术栈方案，每套包括前端、后端、数据库、AI 编排、向量检索、部署，并说明推荐理由、替代方案、风险提醒、学习资源。最后告诉我先做哪个最小 demo 验证。”

AI 可能推荐：第一套，Next.js + TypeScript + Tailwind + FastAPI + Python + LangChain + pgvector + Supabase + Vercel。第二套，Next.js + TypeScript + Supabase + LangChain.js + pgvector + Vercel。然后解释第一套适合 Python AI 生态，第二套适合全 TS 全栈。风险包括 AI API 成本、向量检索质量、PDF 解析复杂度。最小 demo 是先做上传 PDF + 摘要。

你拿到建议后，去查 FastAPI、LangChain、pgvector、Supabase 的官方文档，确认版本和兼容性。跑一个最小 demo，上传一个 PDF，调用 AI 总结，存到数据库。跑通了，再扩展。这就是完整的 vibe coding 选型流程。

## **9.7 本章小结**

Vibe coding 不是让 AI 替你做决定，而是让 AI 加速你的决策和开发。选型时，给 AI 清楚背景和约束，让它给多套方案和取舍，然后你验证、交叉检查、跑最小 demo。适合 AI 编程的技术栈是主流、类型强、文档多、生态大、部署简单的。和 AI 协作时，注意版本、安全、依赖、密钥、审查、小步提交、版本控制。AI 是助手，你是负责人。

下一章是附录，给你一个可以直接复制的“让 AI 帮你选技术栈”提示词模板。你可以把项目信息填进去，发给任何 AI，快速得到分点建议。模板之后，教程就结束了。希望这套内容能帮你建立技术选型的全局认知，少走弯路，多做项目。
